# Migrations a human reviewer has read in full and confirmed STATE-ONLY: they tell Django's model
# state what already happened and emit no DDL, so the destructive-name match in
# tools/checks/migration_ops.py does not apply to them.
#
# One entry per line: <repo path> <the file's exact 40-hex git blob sha>
#
# The blob sha is the whole point. The exemption is granted to a reviewed FILE CONTENT, never to a
# path and never to a shape: change one byte and the blob differs, the exemption lapses, and the
# file is judged like any other. Three RED review rounds (2026-11-24) showed that deciding
# state-only-ness from the source cannot be made to converge, so a human decides it once, here,
# against a named blob.
#
# Adding a line is itself a RED change (tools/checks/* is RED in tools/blast_radius.py), so every
# exemption arrives in a diff under adversarial review. A reviewer accepting one owes, in writing:
#   - the blob sha resolves to the file the entry names (`git rev-parse <sha>:<path>`, or
#     `git cat-file -p <blob>` read in full);
#   - its operations are a SeparateDatabaseAndState whose database_operations list is empty and
#     literal, so the migration runs no DDL;
#   - the SQL check still runs on a listed file, so this line excuses no DROP, TRUNCATE or DELETE.
#
# STATE-ONLY IS THE WHOLE SCOPE. This file is not a general hatch for a destructive migration, and
# in particular not for an AlterField that really reaches the database: a reviewer asked to list one
# refuses. Widening what may go here is Kevin's call, not a reviewer's.
#
# Get a blob sha with:  git rev-parse <commit-ish>:<repo path>
#
