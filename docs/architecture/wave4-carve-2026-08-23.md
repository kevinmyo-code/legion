# Wave 4 carve: fleet onto the engine

Owed by `.scratch/aspect-engine/issues/21-migration-waves.md` point 2 ("per-aspect carve...
produced per wave before its build starts") and ticket 11 answer point 5 (the per-plugin inventory
table). Written before any code in this wave, following [Wave 1](wave1-carve-2026-08-23.md),
[Wave 2](wave2-carve-2026-08-23.md), and [Wave 3](wave3-carve-2026-08-23.md)'s own shape. This is
the biggest and last of the four waves ("fleet onto the engine") - it also inherits the widest
domain: OBD stack, maintenance, service records, fuel/drives, recaps, garage.

## Scope decision, stated up front (instruction 6)

**This wave migrates the core chain completely - vehicles, service records, maintenance items,
odometer - and defers everything else, named below, to a follow-up wave.** The fleet domain is 18
entities wide (17 in `data/local/` plus `CarTask`, already ruled dead by Wave 1 - see below); trying
to carve and migrate all of them in one pass would repeat the exact mistake CLAUDE.md's L10/L11
lessons exist to catch (a grep-clean breadth pass that never gets the one hard entity - the
maintenance clock - actually right). The core chain is also the one instruction 2 names by name
(hands-and-senses ticket 29) and the one with a real, load-bearing correctness bug behind it
(service history and the maintenance clock disagreeing) - it is where the carve work is genuinely
hard, and where getting it wrong would ship the exact drift bug ticket 29 diagnosed straight into
the engine's own schema.

## The finding that reshapes this carve: ticket 29's diagnosis is the carve, not a footnote

`.scratch/hands-and-senses/issues/29-one-source-for-service-history.md` (status `kiv`,
`status-detail: "superseded by the aspect engine... Wave 4"`) is not closed and unrelated - it is
explicitly parked THERE, waiting for THIS wave. Kevin's own diagnosis: *"service history and
maintenance clock should be tied together as one object no? thats why theres the bug."* Traced in
full (`data/local/ServiceRecord.kt`, `data/local/MaintenanceItem.kt`,
`vehicle/VehicleController.kt` lines 533-748): `service_records` (the events - what was actually
done, when, at what mileage) and `maintenance_items.lastDoneMileage`/`lastDoneDate` (the schedule's
own clock, meant to be a projection of those events) are two independently-writable stores of what
is supposed to be one fact. `logServiceDirect` writes both in the same call (line 571 + 608) and
usually keeps them in step, but `MaintenanceItemDao.setAnchor` can move the clock alone (a driver
backfill, an advisor-accepted proposal), and nothing enforces the two ever agreeing - which is
exactly how Kevin's own Jeep ended up with a clock reading 227,483 mi with no date, and a
`service_records` row for the same oil change reading 227,374 mi on 12 Aug, world's most obvious
avoidable disagreement.

**Ticket 29's own recommendation is adopted here, not reopened.** *"Does the override become a
`service_records` row of its own (tagged as asserted rather than observed)... This is the
recommendation."* The carve below does exactly that: one `ServiceHistory` record type carries
BOTH kinds of fact - `kind = OBSERVED` (migrated straight off a real `ServiceRecord` row) and
`kind = ASSERTED` (a user-stated anchor with no backing event, migrated off `MaintenanceItem`'s
`lastDoneMileage`/`lastDoneDate`) - so a screen or a voice answer built against this table cannot
read two different histories the way `ui/FleetScreen.kt`'s Service History section and
`MaintenanceAgent`'s spoken answer used to. The interval DEFINITION (how often, on what axis, who
set it) is schedule configuration, not an event, and stays its own record type, `MaintenanceSchedule`
- ticket 29's own framing: *"Records are the events. The clock is a projection of them, plus an
explicit override."* `MaintenanceSchedule` carries the projection's INPUTS (interval, provenance,
never-done); the actual last-done figure a schedule check would read is `ServiceHistory`, not a
column on `MaintenanceSchedule` at all - the drift is deleted by construction, because there is no
longer a second place for that figure to live.

**What this wave does NOT do: it does not build the schedule math against the new table.** Reading
"is item X due" off the new `ServiceHistory`/`MaintenanceSchedule` pair (the way
`VehicleController.dueItems`/`isDue` today reads `MaintenanceItem.lastDoneMileage` directly) is
cutover work (ticket 14 point 2), same as every other wave - `vehicle/VehicleController.kt` is not
touched by this wave at all. This wave's job is that the SCHEMA and the MIGRATED DATA no longer
have the split; making the live app read it is next.

## `ServiceHistory`'s dedup rule, stated as a judgment call (REASONED)

Every `MaintenanceItem` whose `lastDoneMileage`/`lastDoneDate` is non-null represents a fact that
must survive the migration (CLAUDE.md-adjacent §4 rule 6 posture, applied to migration
completeness the same way Wave 2/3's `failedLineItemGuids`/`anyFailure` folding already does: "no
fact is lost" per ticket 29's own rule). The naive approach - always create an `ASSERTED` row for
every non-null anchor - would duplicate the common case where the anchor and a real `ServiceRecord`
already agree (`logServiceDirect`'s normal, non-drifted path). The other naive approach - try to
match an anchor to "the" corresponding `ServiceRecord` by nearest mileage/date - is exactly the
guessing ticket 29 warns against: *"A migration that guesses is worse than one that asks... prefer
preserving both facts... over silently picking a winner."*

**The rule this migration uses, mechanical and non-guessing:** for a `MaintenanceItem` with a
non-null `lastDoneMileage` and/or `lastDoneDate`, look at every `OBSERVED` `ServiceRecord` already
on file for the SAME `(vehicleId, serviceName)` pair (exact string match - `serviceName` is already
canonicalised identically by every write path per `ServiceRecordDao.getMostRecentForVehicleAndService`'s
own doc comment, so this is not a fuzzy match). If ANY of them has `mileage == lastDoneMileage`
(when `lastDoneMileage` is non-null) OR `date == lastDoneDate` (when `lastDoneDate` is non-null),
the anchor is considered **explained** and no `ASSERTED` row is created - the fact already exists
as an `OBSERVED` row. Otherwise, an `ASSERTED` row is created carrying exactly the anchor's own
`lastDoneMileage`/`lastDoneDate` (nulls preserved as nulls, never invented). This never merges two
facts into one and never discards a value that does not match anything - it only avoids the ONE
case where duplication is provably certain (an exact-value hit on the same vehicle/service). The
Jeep's dateless 227,483 anchor does not match its 227,374/12-Aug `ServiceRecord` on either axis, so
it survives the migration as its own `ASSERTED` row, disagreement and all - **exactly what ticket
29 asked for**: both facts preserved, stated as what they are, not silently reconciled.

`neverDone` is not an anchor at all (`MaintenanceItem`'s own doc: "always overdue... never treated
as due") - it produces no `ServiceHistory` row and is carried instead as a `MaintenanceSchedule`
field.

## What the copier does and does not copy

- **Vehicles first, unconditionally, from `VehicleDao.getAllIncludingArchived()`** - both `ServiceHistory`
  and `MaintenanceSchedule` rows reference a vehicle, so every vehicle (including an archived one -
  archived means hidden from the roster/picker, not deleted, and its history is exactly as real)
  must exist as an `EngineRecord` before any child row can validate its reference, the same ordering
  discipline Wave 2's receipts-before-line-items and Wave 3's (implicit, single-record-type) shape
  both already establish.
- **`ServiceRecord` rows, `WHERE deleted = 0` only** (`ServiceRecordDao` has no `getAll()`; a new
  `getAllIncludingDeleted()` is NOT added - deliberately: unlike `MaintenanceItemDao.getForVehicleIncludingDeleted`
  (which exists for a real reader, the populate diff), nothing needs a tombstoned `ServiceRecord` for
  this migration, and CLAUDE.md's own posture toward `service_records.deleted`'s doc comment - "this
  tombstone is LOCAL ONLY and CANNOT propagate across devices" - argues for treating a tombstoned row
  as genuinely gone here, matching how the OLD app already treats it everywhere except sync's raw
  snapshot).
- **`MaintenanceItem` rows, `WHERE deleted = 0` only** (`MaintenanceItemDao.getForVehicle`, already
  filtered) - a tombstoned schedule item is, per that entity's own doc comment, a driver-deleted row;
  carrying its interval OR its anchor forward as live engine data would resurrect something the
  driver removed, the same "don't resurrect a tombstone" posture Wave 1's `ListItem`/`TaggedPlace`
  filtering already states.
- **`ServiceHistory` copies happen in two passes per vehicle**: every `OBSERVED` row first (off
  `ServiceRecordDao`), THEN every `ASSERTED` row (off `MaintenanceItemDao`, applying the dedup rule
  above against the `OBSERVED` rows already read for that same vehicle+service in this pass) - so
  the dedup check always has the full `OBSERVED` set for that pair in hand before deciding whether an
  anchor is explained.
- **Preserves timestamps.** Neither `ServiceRecord` nor `MaintenanceItem` carries a real insert-time
  clock distinct from its own subject-matter timestamp - `ServiceRecord.date` (when the service
  happened) and `MaintenanceItem.updatedAt` (last schedule edit) are the closest anchors, same
  "closest available anchor, not a bookkeeping clock" substitution Wave 2/3's carves already state
  and name as deliberate rather than implicit. `Vehicle` similarly has no creation timestamp; its
  `updatedAt` is used for both clocks, same shape.
- **Identity**: `ServiceRecord.syncId` reused directly; every other row in this wave (`Vehicle`,
  `MaintenanceSchedule`, `ServiceHistory` `ASSERTED`) gets a deterministic `UUID.nameUUIDFromBytes`
  guid off its own natural key, per the field-mapping tables above - never a fresh random UUID,
  so a second run recognizes and skips what it already wrote.
- **Provenance is unconditionally `RecordProvenance.USER`** for every row this wave writes, across
  all three record types. Nothing here passed through CLAUDE.md §4's reconciliation gate (fleet has
  no document-ingestion path at all) - every fact originated from the driver speaking to LEGION or
  typing into a form, matching Wave 1's `USER` reasoning exactly ("a straight field-by-field copy has
  no stated total to reconcile against... not even an ingestion path at all").

## Owed follow-ups, named rather than silently dropped

1. **Cutover per aspect** (ticket 14 point 2) is explicitly NOT this wave's job. `vehicle/`, every
   fleet screen (`ui/FleetScreen.kt` and friends), and every fleet `LiveToolbox` tool keep reading
   and writing the legacy `vehicles`/`service_records`/`maintenance_items` tables unchanged until
   this aspect is verified on the A25 and cut over in its own later commit - the schedule-math
   re-point (`VehicleController.dueItems`/`isDue` reading `ServiceHistory`/`MaintenanceSchedule`
   instead of `MaintenanceItem`'s own anchor columns) happens THERE, not here.
2. **`BuildEntry`, `VehicleSpec`, `OilAnalysis`, `MonthlyRecap`, `DailyDriveLog`, `YearlyWrapped`,
   `Drive` are deferred to a named follow-up wave** (Wave 5, fleet-continued) - each with its own
   one-line reasoning in the carve table above, not silently dropped.
3. **`OdbSample`/`CodeEvent`/`CodeClearEvent`/`VehicleCapability`/`DriveReassignment`/`ChassisQuirk`/
   `ForesightNote` stay plugin-internal, permanently** by this carve's own ruling - not a deferral,
   a decision, matching the guiding line's own "high-frequency telemetry and transient OBD state
   stay plugin-internal" instruction.
4. **`Vehicle.personaPrompt`/`voiceName`/`personaTraits`/`archived`/`onboarded`/
   `lastOdometerPromptAt`/`tripMilesSinceBaseline` are not carried as fields** - named in the field
   mapping table above with per-column reasoning, revisited only if a follow-up wave's cutover finds
   a live need for one of them on the record.
5. **`ServiceHistory`'s `ASSERTED`/`OBSERVED` dedup rule is intentionally conservative** (see its own
   section above) - it can under-collapse (an anchor that is a near-miss but not an exact match on
   either axis still gets its own `ASSERTED` row, even in cases a human would recognize as "the same
   event") but it can never silently drop or merge a fact. Named as a deliberate false-negative-safe
   choice, not re-litigated here.
6. **Neither legacy table is dropped.** `vehicles`, `service_records`, and `maintenance_items` stay
   exactly as they are today; this wave adds new tables' worth of DATA (rows in
   `aspects`/`record_types`/`field_defs`/`records`), not a schema change to any existing table -
   matching every prior wave's own closing note.
7. **`VehicleDao.getAllIncludingArchived()` and `ServiceRecordDao`'s existing filtered queries are
   reused as-is; no new DAO query was needed for `Vehicle`/`ServiceRecord`.** `MaintenanceItemDao.getForVehicle`
   is likewise reused unchanged. No Room schema/version change anywhere in this wave.
