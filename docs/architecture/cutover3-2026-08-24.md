# Cutover 3: Ledger becomes engine-native

Owed by `.scratch/aspect-engine/issues/22-cutover-per-aspect.md` ("Cutover per aspect: the engine
becomes the read and write path"). Written before this doc's own author claims the branch is done,
per CLAUDE.md §8's L11 ("a ticket's own verification steps are gates, not notes") - the same
discipline `cutover1-2026-08-24.md`/`cutover2-2026-08-24.md` set, and the worked example this doc
follows rather than re-deriving its own shape from scratch.

**This is the highest-stakes of the three cutovers so far** - ledger is the one aspect whose data
carries CLAUDE.md §4's reconciliation provenance for real, including rule 7's provisional-row
supersession. The reconciliation gate itself (`ledger/LedgerStatementAgent`, the deterministic
parsers, `resolveDedup`, `buildBudgetVsActual`) is **byte-for-byte untouched** by this branch - see
`docs/architecture/wave3-carve-2026-08-23.md`'s own finding: the gate runs entirely upstream of any
write, exactly as cutover 2 found for pantry. What cutover 3 changes is only WHERE a gate-passed
result lands, and where rule 7's transience guarantee is enforced.

## What "cutover" means here, precisely

Before this branch: the engine held a COPY of every `LedgerTransaction` (wave 3), but nothing read
or wrote it - `LedgerController`/`IngestPipeline` were still 100% legacy-table-backed, and the engine
copy was reconciled by `EngineDataMigrationWave3`'s own per-call pass, dead weight otherwise, exactly
like wave 1/2's notes/places/pantry before their own cutovers.

After this branch: `LedgerController`/`IngestPipeline` are internally engine-backed (every read and
write goes through `RecordStore`/`EngineRecordDao` against the Ledger aspect's `Transaction` record
type), and every caller - `ui/LedgerImportActivity`, the Money tab screens, `service/LiveToolbox.kt`'s
ledger tools, `advisor/digest/CredDigestBuilder`/`HomeDigestBuilder`, `goals/GoalProgress` - keeps
calling the SAME public functions, unchanged (ADR 0035: "the controller keeps its seam"). The legacy
`ledger_transactions` table is **frozen for new content** - every value a user sees or acts on from
this branch forward was written through the engine, never the legacy DAO. `ingested_files`
(per-file ingestion ledger), `categories`/`category_rules` (classification vocabulary), and
`budget_targets` stay plugin-internal and legacy-backed, unchanged - `wave3-carve-2026-08-23.md`'s
carve table already ruled all three off the engine, and nothing here re-opens that ruling.

## The commit-transaction design

`IngestPipeline.commit`'s `Success` branch, in order, all inside ONE `db.withTransaction` block:

1. **Replace-flow deletion** (`staged.isReplace`): every ACTIVE engine `Transaction` record whose
   `sourceFileId` field equals the incoming `driveFileId` is trashed via `RecordStore.delete` - the
   engine-side equivalent of the retired `LedgerTransactionDao.deleteBySourceFileId`. Any
   non-`Trashed`/non-`AlreadyTrashed` result throws `EngineWriteFailedException`.
2. **Rule 7 supersession, engine-side, in the same transaction as the insert that follows.** When
   `stamped.first().ingestMethod != UNRECONCILED` (a reconciled file), every ACTIVE engine
   `Transaction` record tagged `RecordProvenance.UNRECONCILED` for the SAME physical card (`sameCard`,
   suffix-matched exactly as the retired legacy query `deleteSupersededProvisional` was) whose
   `txnDate` falls inside the incoming statement's own `[minDate, maxDate]` range is trashed. The
   three load-bearing properties the legacy version's own doc comment named are preserved exactly:
   **the guard** (an `UNRECONCILED` file can never supersede anything, including its own prior
   import), **before the dedup read** (a stale provisional row must not survive to be matched as a
   duplicate and drop the verified row that was meant to replace it), **inside the transaction** (a
   crash between the delete and the insert can never leave the account with neither).
3. **Dedup read**, now against the ENGINE mirror (`activeByRecordType`, converted via
   `LedgerRecordBridge.toTransaction`) instead of `getForAccountInRange`, read AFTER steps 1-2 so it
   never sees a row that was just trashed. `resolveDedup` itself - the pure per-tuple counting
   function - is REUSED VERBATIM, untouched by this cutover; only its data source changed.
4. **Insert**, one `RecordStore.create` per `resolveDedup`'s `toInsert` row, provenance mapped via
   `LedgerRecordBridge.provenanceFor(txn.ingestMethod)`, `guid = txn.syncId`. Any
   `WriteResult.Failure` throws.
5. `ingested_files` bookkeeping (`ingestedDao.upsert`) - unchanged, still legacy, still inside the
   same transaction.

**Any exception anywhere in steps 1-5 rolls the WHOLE transaction back** (Room's `withTransaction`
rolls back on a thrown exception, never a plain early return - the same primitive
`pantry/PantryController.writeReceipt` already established for a receipt-plus-items write). The
`try`/`catch` sits OUTSIDE `db.withTransaction`, catching `EngineWriteFailedException` after Room has
already rolled back, then writes the file's `IngestedFile` record back to `IngestState.NEW` (OUTSIDE
the rolled-back transaction, as its own write) so the file is re-offered on the next scan rather than
vanishing, and returns `CommitOutcome.EngineWriteFailed(reason)` - a worded failure (CLAUDE.md §7),
never a false success. `LedgerController.commitResult` and the folder-scan service that sat beside
it both handled this new sealed-class case exhaustively at the time (Kotlin's `when` forced both
call sites to be updated at compile time). **Both are gone now** - backend-erp ticket 25
(2026-08-29) deleted phone-side statement ingestion entirely, `commitResult` and the scan service
included; this paragraph is historical record of the cutover, not a live code path.

## Rule-7 semantics: what changed and what did not (a fork, resolved rather than surfaced blind)

**Not a semantic change** - the supersession RULE itself (which rows get trashed, on what
guard, in what order, relative to what read) is preserved exactly; only its storage layer moved.
This was checked, not assumed: every one of the three load-bearing properties the legacy
`deleteSupersededProvisional` caller comment named is still true of the engine-side version, and the
new `IngestPipelineEngineCommitTest`'s supersession test pins the exact in-window/out-of-window/
non-`UNRECONCILED` boundary the legacy SQL query enforced (`substr(accountId, -4) = substr(:accountId,
-4) AND txnDate BETWEEN :fromMs AND :toMs AND ingestMethod = 'UNRECONCILED'`), now expressed as a
Kotlin filter over `sameCard`/date-range/provenance instead of SQL.

**What DID change, stated rather than left implicit**: before this branch, `RecordStore.delete`
trashes (30-day restorable) rather than hard-deleting the way the legacy `DELETE FROM
ledger_transactions WHERE ...` did. This is a strictly SAFER guarantee, not a weaker one - a
superseded provisional row is now recoverable for 30 days instead of gone the instant it is
superseded - and it costs nothing: no surface reads trashed rows (`activeByRecordType` excludes
them everywhere), so a driver-visible balance/total is identical either way. Same reasoning
`LedgerController.purgeAll`'s own doc comment now states for its own move onto `RecordStore.delete`.

## What retired

**`EngineDataMigrationWave3.reconcileSupersededProvisional`'s automatic per-call invocation is
retired.** Wave 3 originally ran this pass on EVERY call to `copyLedgerIfNeeded`, including the fast
path, because the ONLY place rule-7 supersession happened was the legacy table, and a purely additive
copier could not mirror a deletion any other way. Cutover 3 moves supersession itself into
`IngestPipeline.commit`'s own engine-side transaction (see above) - a newly superseded provisional row
is trashed at write time now, in the exact same transaction as the write that supersedes it, so the
reconciliation pass is no longer needed on every call.

**The function itself is KEPT, not deleted** - its doc comment's own reasoning ("an additive-only
copier cannot mirror a deletion") still holds for exactly one remaining case: legacy-table
supersession that happened BEFORE this cutover branch's `IngestPipeline` took over (the historical
window between wave 3's original landing and this build). `EngineDataMigrationWave3.catchUpOnce` -
new this branch, same shape as `EngineDataMigrationWave1.catchUpOnce`/`EngineDataMigrationWave2.catchUpOnce`
- calls it exactly once, guarded by its own SharedPreferences marker
(`cutover3_catchup_v1_completed`), after re-running the ordinary additive copy. `EngineDataMigrationWave3.Result`
lost its `supersededTrashed` field (no longer meaningful for `copyLedgerIfNeeded`'s own per-call
return value, since that pass no longer runs the reconciliation step) - `EngineDataMigrationWave3Test`
was updated to assert `catchUpOnce`'s effects directly instead (four tests, listed below), not deleted.

**Neither `LedgerTransaction` nor `IngestedFile` is dropped.** Both stay exactly as they are today -
this branch rewires WRITE and READ paths, not schema; no `app/schemas/` diff, no migration, no
version bump.

## The bridge: how the controller keeps its seam

Every public `LedgerController` function keeps its exact pre-cutover signature and return type
(`LedgerTransaction`/`AccountBalance`/`BudgetVsActual`/`CategorySetResult`/etc - the legacy Room-row-
shaped value objects), so every caller flips with zero changes of its own:

- **`LedgerRecordBridge`** (new, `engine/ledger/`) is the ONE place `LedgerTransaction` <->
  `EngineRecord` translation happens - `fieldValuesFor`/`toTransaction`/`provenanceFor`/
  `ingestMethodFor`. Used by `IngestPipeline`, `LedgerController`, AND `EngineDataMigrationWave3` (the
  migration's own inline field map and provenance `when` were extracted into this file rather than
  left duplicated three ways - the exact drift risk CLAUDE.md's lessons ledger warns about).
- **`LedgerController.allTransactions(context)`** is the one read every other function funnels
  through - reads every active `Transaction` engine record, converts via `LedgerRecordBridge`. Every
  DAO-query-shaped read (`getForAccountInRange`, `getForCurrencyInRange`, `allAccountIds`,
  `accountIdsForCurrency`, `currencyForAccount`, `earliestTxnDate`/`latestTxnDate`,
  `uncategorizedTransactions`, `categoryPendingRows`, etc.) is now a Kotlin filter/aggregate over this
  one in-memory list, same "personal household app's data volume, not an enterprise table scan"
  tradeoff `RecordStore`'s own class doc already accepts, and the same one
  `pantry/PantryController.allReceipts`/`allLineItems` already applies.
- **Every PURE business-logic function this codebase already had - `resolveDedup` (`LedgerDedup.kt`),
  `analyzeTransfers`/`operatingExpenses` (`LedgerTransfers.kt`), `buildBudgetVsActual`
  (`LedgerBudget.kt`), `sameCard`/`matchesAccountFilter`/`maskedAccountLabel`
  (`LedgerAccountIdentity.kt`), `extractMerchantKey`/`isBankNoiseKey`/`matchCategory`
  (`Categorization.kt`), `coversMonthWithoutGaps`/`coveredThroughMs` (`LedgerCoverage.kt`) - is
  REUSED VERBATIM, zero changes.** Every one of them operates on `List<LedgerTransaction>` value
  objects, never on a DAO directly, so converting engine records into that same value-object shape
  (exactly cutover 2's own insight for pantry's chart/row pure functions) means the entire
  transfer-detection, budget-vs-actual, and dedup logic needed no changes at all - only WHERE the
  `List<LedgerTransaction>` comes from changed.
- **Category application** (`applyCategoryRules`/`applyCategoryGuesses`/`confirmCategoryGuess`/
  `setCategory`/`recategorize`) - previously raw `UPDATE ledger_transactions SET category = ...`
  queries - now read the matching rows out of `allTransactions`, then write each one through
  `RecordStore.update` inside one `db.withTransaction` per bulk call (`updateCategoryOnRows`), the
  same "multi-row write gets a transaction" discipline `IngestPipeline`'s commit already established.
  A per-row `WriteResult.Failure` is logged and excluded from the returned count rather than silently
  dropped - CLAUDE.md §7's "in words what did NOT happen" applied to a bulk write.
- **`purgeAll`** now trashes every active engine `Transaction` record via `RecordStore.delete` (loop,
  inside one `db.withTransaction` alongside the `ingested_files` wipe) instead of one bulk
  `DELETE FROM ledger_transactions` - see "What DID change" above for why trash-not-hard-delete is a
  strictly safer replacement, not a weaker one.

## Dedup discipline (point 5)

`LedgerController`'s pre-cutover cross-file dedup was two-layered: `resolveDedup` (pure, per-tuple
counting, `LedgerDedup.kt` - REUSED VERBATIM) plus a DAO-backed candidate-set fetch
(`getForAccountInRange`) that fed it. The fetch moved onto the engine (`allTransactions` filtered by
account/date-range, both inside `IngestPipeline.commit`'s transaction and in
`LedgerController.dedupAgainstExisting`'s `importWithoutRecord`/`commitPlain` fallback path); the
comparison logic itself did not change at all. `IngestPipelineEngineCommitTest`'s "an exact duplicate
row from an overlapping re-import is skipped" test pins this end to end against real engine writes -
a second, overlapping statement restating an identical transaction (same account/date/cents/
description, different `lineRef`) is skipped, and a genuinely new row from the same statement still
lands.

## Senior review, 2026-08-24: one blocking finding, one should-fix (both taken)

**BLOCKING - `catchUpOnce` first-launch race.** `reconcileSupersededProvisional`'s original logic
trashed any active engine `UNRECONCILED` `Transaction` record whose `guid` was missing from legacy
`allSyncIds()`. Post-cutover, `IngestPipeline.commit`/`LedgerController.logPendingTransaction`
create BRAND-NEW engine `UNRECONCILED` rows whose `guid` was NEVER written to the legacy table
(`ledger_transactions` has zero writers, per this doc's own ruling table) - such a `guid` is, by
construction, always "missing" from legacy. A driver importing a card CSV or voice-logging a pending
transaction on first launch, before the fire-and-forget `catchUpOnce` coroutine finishes, would have
that legitimate row silently trashed with nothing superseding it - rule 7 inverted.

**Fix chosen: a persisted, positively-tracked migrated-guid set**, not a `createdAt`-cutoff (the
review's other offered shape). `createdAt` was checked, not assumed, and ruled out: both the copier
and `IngestPipeline.commit`'s own create call pass `now = txn.txnDate` to `RecordStore.create` (the
field-mapping doc comment's own "closest available anchor" reasoning), so `EngineRecord.createdAt`
reflects the TRANSACTION'S OWN DATE for both a migrated row and a live-imported one, never wall-clock
insert time - a timestamp cutoff would have been silently wrong on real data (a transaction dated
yesterday, imported ten seconds ago, reads as "older" than any reasonable catch-up cutoff).
`EngineDataMigrationWave3.copyLedgerIfNeeded` now records every `guid` it confirms as legacy-derived
(newly created OR found already-copied on a rescan) into a SharedPreferences string set
(`migrated_guids_v1`); `reconcileSupersededProvisional` gates on membership in that set BEFORE ever
asking whether a guid is missing from legacy. A live-imported row's `guid` (a fresh UUID, never
touching the frozen legacy table) can never be a member, so it is structurally exempt regardless of
timing - no race window exists to lose. Full reasoning is in `EngineDataMigrationWave3.kt`'s own
class doc and `reconcileSupersededProvisional`'s doc comment. New tests: `EngineDataMigrationWave3Test`'s
`catchUpOnce never trashes an engine-native row whose guid was never in the legacy table, even if
created before reconcile runs` (the exact race) and `catchUpOnce still trashes a genuinely migrated
row once its legacy backing disappears, proving the new gate isn't overbroad` (the positive control -
proves the fix didn't just make reconciliation trash nothing at all).

**SHOULD-FIX (pre-existing, taken now because ledger's multi-row commits make it hot) - `RecordStore`'s
`_afterWrite.tryEmit` fires INSIDE the caller's `withTransaction`.** Traced end to end rather than
changed: the only production subscriber (`MirrorLifecycleBinder`) always routes through
`MirrorSync.scheduleExport()`, which unconditionally delays 5 seconds before touching Room and then
reads fresh via DAO calls at read time - several orders of magnitude past how long a ledger/pantry
multi-row `db.withTransaction` block takes to settle, and independent of that margin, Room's own
transactional isolation means a reader outside a transaction cannot observe its uncommitted writes at
all. No code change; `RecordStore.kt`'s `afterWrite` doc comment now carries the full traced
justification. Deliberately NOT covered by an automated test - a genuine cross-connection commit/
rollback race is not something Robolectric's single-process SQLite harness can be trusted to
reproduce meaningfully, so this is stated as `traced`, not `tested`.
