# Wave 3 carve: ledger onto the engine

Owed by `.scratch/aspect-engine/issues/21-migration-waves.md` point 2 ("per-aspect carve... produced
per wave before its build starts") and ticket 11 answer point 5 (the per-plugin inventory table).
Written before any code in this wave, following [Wave 1's carve](wave1-carve-2026-08-23.md) and
[Wave 2's carve](wave2-carve-2026-08-23.md)'s own shape and reusing their reasoning rather than
repeating it. This is the "gate re-plumb" wave named in ticket 14's answer point 1 - the highest-
stakes of the four, because this is the one aspect whose data carries CLAUDE.md §4's reconciliation
provenance for real, including rule 7's provisional rows.

## The finding that reshapes this carve: `ingestMethod` maps directly onto `RecordProvenance`

`LedgerTransaction.ingestMethod` is `IngestMethod { DETERMINISTIC, LLM_RECONCILED, UNRECONCILED }`.
`RecordProvenance` (`data/local/EngineRecord.kt`) is `{ DETERMINISTIC, LLM_RECONCILED, UNRECONCILED,
USER }`. The first three spellings are IDENTICAL. This was verified by reading both enum
declarations side by side, not assumed from the names alone - `EngineDataMigrationWave3.provenanceFor`
is a plain, exhaustive Kotlin `when` with **no `else` branch**, mapping each of the three
`IngestMethod` values to the identically-named `RecordProvenance` value and nothing else. `USER` is
never produced by this wave - every `LedgerTransaction` row, without exception, came from a document
or a spoken pending-log entry, never a hand-authored record the way Wave 1's `ListItem`/`TaggedPlace`
were.

**On "if other values exist in the column, STOP and surface": traced, not assumed.** No custom
`TypeConverter` for `IngestMethod` exists anywhere in `data/local/` (confirmed by grep) - Room 2.6+'s
native Kotlin-enum column support is what's in play, which means Room itself calls
`IngestMethod.valueOf(...)` while reading a row out of SQLite and **throws before a
`LedgerTransaction` Kotlin instance can ever exist** if the stored string doesn't match one of the
three declared constants. By the time `EngineDataMigrationWave3` holds a `LedgerTransaction` object
in Kotlin, its `ingestMethod` is structurally guaranteed to be one of the three - "a fourth value
reaches the copier" is not a runtime case to defend against, it is a compile-time impossibility once
the row was successfully read at all. Nothing was found that would trip this stop condition, and the
reasoning for why nothing could is written into the copier's own class doc, not merely asserted here.

## Field mapping: `LedgerTransaction` -> Ledger aspect, `Transaction` record type

`description`, `amount`, `lineRef` - every field a `LedgerTransaction` row carries non-nullably
today. `balance`, `sourceFileId`, `category`, `pendingLoggedAt` are optional, matching their
nullable legacy columns exactly. `categoryPending` is required (it is a non-nullable `Boolean` on
the legacy row, always `false` or `true`, never absent).

## Reconciliation status, quarantine, and provenance

- **Provenance maps directly, per-row, from `ingestMethod`** - see the finding above. Never
  upgraded (an `UNRECONCILED` row never becomes `LLM_RECONCILED` by migrating), never collapsed
  (all three stay distinct), never defaulted to `USER`.
- **Money is carried as `Long` cents, unchanged, at every step** - `amountCents`/`balanceCents` copy
  straight through with no floating-point conversion, matching CLAUDE.md §4 rule 3. Sign is
  preserved exactly (a debit stays negative).
- **No quarantine state exists to exclude, and this is a stronger claim than Wave 2's equivalent
  finding, not the same one.** Wave 2 found pantry has NO quarantine state anywhere. Ledger DOES
  have quarantine state (`IngestedFile.state == QUARANTINED`, with a `quarantineReason`) - but it
  lives entirely on `ingested_files`, which is plugin-internal and not migrated (see the carve
  table). **Zero rows are ever written to `ledger_transactions` for a quarantined file** -
  `IngestPipeline.commit`'s `is LedgerIngestResult.Quarantined ->` branch only ever writes to
  `ingestedDao`, never to `txnDao` (read in full, `ledger/IngestPipeline.kt` lines 247-259). So
  every `LedgerTransaction` row this migration will ever find already passed CLAUDE.md §4's gate in
  one of its three legal shapes (rules 1-2 for `DETERMINISTIC`/`LLM_RECONCILED`, rule 7 for
  `UNRECONCILED`) by the time it reached Room - the migration is a faithful COPY of that state, not
  a re-verification of it.

## Rule 7's transience guarantee: where supersession lives, and the dual-copy plan

**Supersession lives in `ledger/IngestPipeline.commit`, operating directly on the LEGACY
`ledger_transactions` table, inside a `db.withTransaction` block, gated on
`stamped.first().ingestMethod != IngestMethod.UNRECONCILED`** (`IngestPipeline.kt` lines 284-301,
calling `LedgerTransactionDao.deleteSupersededProvisional`). Read in full: when a reconciled
(`DETERMINISTIC`/`LLM_RECONCILED`) statement commits, it first deletes any `UNRECONCILED` rows for
the same card (suffix-matched on the last 4 digits, per `sameCard`) whose `txnDate` falls inside the
incoming statement's own date range - BEFORE reading `getForAccountInRange` for dedup, and INSIDE
the same transaction as the insert, so a crash mid-commit can never leave the account with neither
the provisional nor the reconciled rows. A second deletion path exists alongside it:
`LedgerTransactionDao.deletePendingById` (`clear_pending_transaction`'s voice tool), which removes a
single voice-logged `pendingLoggedAt`-tagged row (also always `UNRECONCILED` - see that column's own
doc comment) once a user says it cleared. **Both of these keep operating on the legacy table only,
unchanged by this wave** - per instruction 5, nothing about `ledger/IngestPipeline` or
`ledger/LedgerController` is touched here.

**This means an engine-side `UNRECONCILED` copy of a provisional row can go stale the moment the
legacy row it was copied from is deleted by either path**, unless something on the engine side is
told to catch up. Two options were on the table, per instruction 2:

1. **The copier is re-runnable per-file/per-call**, and each run reconciles supersession itself.
2. **Cutover happens before the next ingestion event** that could trigger supersession, so the
   engine copy is never asked to represent a state past the one it was built from.

**Option 1 is what the code supports, and what this wave builds.** `EngineDataMigrationWave3`'s copy
half is additive-only (same as Wave 1/2 - it can never delete a mirrored row that a legacy row still
justifies), so option 1 as stated cannot fully close the gap by itself; a purely additive re-run
would keep ADDING newly-reconciled rows but would never notice a provisional row's legacy backing
had disappeared. **The copier therefore adds a fourth capability beyond the additive copy: a
`reconcileSupersededProvisional` pass**, run at the end of every call INCLUDING the fast path (the
one deliberate departure from Wave 1/2's "flag set, later calls do nothing at all" shape - see
`EngineDataMigrationWave3.Result`'s own doc comment). It compares the LIVE set of legacy `syncId`s
against every active engine `Transaction` record tagged `RecordProvenance.UNRECONCILED`, and trashes
(via `RecordStore.delete` - 30-day restorable, never a hard delete) any whose legacy row is gone.
This closes rule 7's specific guarantee - an `UNRECONCILED` engine record cannot outlive the legacy
row it mirrors, **as long as the copier is called again after the legacy-side deletion happens** (an
app start, per the `MidnightApplication` wiring below).

**What this does NOT close, named rather than silently accepted**: a `DETERMINISTIC`/
`LLM_RECONCILED` engine record whose legacy row is deleted by a replace-flow re-import
(`IngestPipeline`'s `staged.isReplace` branch calling `deleteBySourceFileId`) or by
`LedgerController.purgeAll` (the admin nuke) is **not** trashed by this pass - it is scoped
deliberately to `UNRECONCILED` only, because that is the provenance rule 7 actually places a
transience obligation on. A stale reconciled engine record surviving a legacy replace/purge is a
real gap, but it is not the gap CLAUDE.md §4 rule 7 exists to close, and closing it would mean
diffing the WHOLE table every call rather than the bounded `UNRECONCILED` subset - left to the
cutover wave, where the copier's job ends anyway (see owed follow-ups).

**Both copies therefore do not fully agree at every instant** - the legacy table is authoritative
and live at all times; the engine copy is a periodically-reconciled mirror, correct as of its last
run, with the one specific staleness mode above named and accepted rather than hidden. This is
consistent with instruction 5: nothing about the legacy ingestion path reads from or defers to the
engine copy in this wave.

## Owed follow-ups, named rather than silently dropped

1. **Cutover per aspect** (ticket 14 point 2) is explicitly NOT this wave's job. `ledger/`,
   `ui/LedgerImportActivity` (and any ledger screens), and every `LiveToolbox` ledger tool keep
   reading and writing the legacy `ledger_transactions`/`ingested_files`/`categories`/
   `category_rules` tables unchanged until this aspect is verified on the A25 and cut over in its
   own later commit.
2. **`Category`/`CategoryRule` are not migrated in this wave** - named above, deferred to cutover,
   where the choice between "stay plugin-internal forever" and "become a migrated record type with
   `category` promoted to a real `FieldType.REFERENCE`" can be made deliberately rather than
   defaulted into here.
3. **`reconcileSupersededProvisional` does not cover `DETERMINISTIC`/`LLM_RECONCILED` legacy
   deletions** (replace-flow re-import, `LedgerController.purgeAll`) - named in the dual-copy plan
   section above, not silently accepted. If cutover is delayed long enough that this gap matters in
   practice (a replace-flow re-import or a purge happening while the engine copy is still being
   relied on for anything), the fix is either widening the reconciliation pass to the whole table
   (accepting the larger scan cost) or simply not treating the mirror as authoritative for anything
   until cutover - which is this wave's actual posture today (instruction 5: old tools/screens keep
   working, unchanged, and are the only thing anything reads).
4. **Neither `LedgerTransaction` nor `IngestedFile` is dropped.** They stay exactly as they are
   today; this wave adds new tables' worth of DATA (rows in `aspects`/`record_types`/`field_defs`/
   `records`), not a schema change to any existing table - matching Wave 1 and Wave 2's own closing
   notes.
5. **`LedgerTransactionDao.getAll()`/`allSyncIds()` are new** (this wave adds them) but are plain
   additive `@Query`s, not a Room schema change - no migration, no version bump, no `app/schemas/`
   diff.
6. **`RecordStore.create` has no reachable "record type is missing" failure path for THIS wave's
   schema, traced rather than assumed.** `LedgerAspectSeeder.ensureSeeded` self-heals a missing
   aspect/record type/field set unconditionally at the top of every call, and
   `EngineDataMigrationWave3.copyLedgerIfNeeded` calls it fresh at the top of every one of its own
   calls - so a record type deleted between two calls is always repaired before the next copy pass
   ever runs. Since `Transaction` also carries no `FieldType.REFERENCE` field (deliberately - see
   the field mapping table), the ONLY other validated failure trigger `RecordStore.create` has,
   this record type structurally cannot produce a `WriteResult.Failure` through any input this
   migration would ever hand it in practice. `EngineDataMigrationWave3Test`'s forced-failure tests
   still exercise the fold-in logic for correctness (defensive code for a case this wave cannot
   naturally trigger) by temporarily corrupting the already-seeded `sourceFileId` field's type to
   `REFERENCE` - see that test file's own doc comment for why that is a legitimate substitute lever,
   not the same lever Wave 2 used.
