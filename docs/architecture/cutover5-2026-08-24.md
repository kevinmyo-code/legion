# Cutover 5: the widget pager becomes the app's home

Owed by `.scratch/aspect-engine/issues/22-cutover-per-aspect.md` point 4 ("The pager becomes the
app home ... MainActivity's fate"), the last open item on that ticket now that cutovers 1-4 have
each landed and been merged (`cutover1-2026-08-24.md` through `cutover4-2026-08-24.md`). Written
before this doc's own author claims the branch is done, per CLAUDE.md §8's L11 - the same
discipline the four prior cutover docs already set, and the worked example this doc follows.

**This is the smallest of the five cutovers by lines changed, and the one with the widest blast
radius by definition** - it is the one branch that touches what every session opens the app onto.

## The flip mechanism, and why

**Chosen: MainActivity hosts the pager as an ordinary `composable(LegionRoute.DASHBOARD)`
destination inside its existing `NavHost`, as its new `startDestination`. `WidgetPagerActivity` -
the separate, `exported="false"`, `adb shell am start`-only Activity ticket 18 shipped the pager
behind - is DELETED.**

**Rejected: moving the `LAUNCHER` `<intent-filter>` to `WidgetPagerActivity` and making it the
real entry point.** `MainActivity.onCreate`/`onNewIntent`/`onResume` carry real, load-bearing
lifecycle wiring that has nothing to do with which screen is on top:

- `readDeepLinkExtras` - `EXTRA_ROUTE` (five live callers: `LedgerIngestService`,
  `LiveSessionController` x3, `ReminderAlarmReceiver`) and `ReminderAlarmReceiver.EXTRA_OPEN_ITEM_ID`.
- The Spotify OAuth redirect (`com.kevin.legion://spotify-callback`), consumed via `intent.data` and
  exchanged in a `LaunchedEffect` above the `NavHost`.
- `onResume`'s three real side effects: `AssistantIgnition.resumeIfEnabled` (the foreground-service
  microphone-type re-promotion), `LocationController.init` (permission-grant-return detection),
  `SyncEngine.maybeAutoSync`, `SpotifyController.connectSilently`.
- `android:launchMode="singleTask"`, required for the Spotify redirect to land in `onNewIntent`
  rather than spawn a second instance.
- "Hey Google, ask LEGION X" (`MEDIA_PLAY_FROM_SEARCH`), also filtered on this Activity.

Making `WidgetPagerActivity` the launcher would mean either duplicating every one of those (a
second, competing copy of lifecycle wiring that already drifted once when `SavedPlacesActivity`/
`LedgerImportActivity`/`PantryImportActivity` existed as separate Activities - ticket 07's own
resolution deleted them for exactly this reason) or routing all of it through a second Activity
that would need `MainActivity`'s own private mutable state, which is not exported. **Hosting the
pager AS a `NavHost` destination inside the Activity that already owns all of this wiring makes the
flip a route-table change, not a lifecycle-wiring change** - zero lines of `onCreate`/`onNewIntent`/
`onResume` touched, and every one of the five `EXTRA_ROUTE` callers above needed zero changes,
confirmed by grep (`docs/architecture/cutover5-2026-08-24.md`'s own verification below).

## The reachability ruling table

Every destination reachable from `MainActivity`'s tab home before this branch, ruled reachable-from-
pager / stays-as-activity / dies. Enumerated from `ui/MainActivity.kt`'s `NavHost` block in full,
not sampled.

| Destination | Before | After | How |
|---|---|---|---|

| `LegionRoute.TODAY` (agenda, ALERTS pane, category drilldown, media mini-bar) | Start destination, HOME hard key | **reachable-from-pager** | The HOME page's own "CLASSIC" button (`WidgetPagerRoot`'s header) |
| `LegionRoute.FLEET` (vehicles, drives, maintenance, UPLINK/telemetry drilldown) | FLEET hard key | **stays-as-activity + reachable-from-pager** | FLEET hard key (unchanged) AND the Fleet aspect page's "OPEN FULL SCREEN" button |
| `LegionRoute.FLEET_PLACES` | Sub-route of FLEET | **reachable-from-pager** | The Places aspect page's "OPEN FULL SCREEN" button (new path); also still reachable through FLEET's own UPLINK panel, unchanged |
| `LegionRoute.FLEET_CARS`, `FLEET_TELEMETRY`, `DRIVING` | Sub-routes/drilldowns of FLEET | **stays-as-activity** | Unchanged, reached from inside FLEET exactly as before |

| A user-created aspect page (the pager's own "+" page) | Did not exist | **reachable-from-pager, no legacy fallback** | The created aspect's own page - never had a legacy screen to fall back to |

**Nothing on the "before" side of this table is unreachable after this branch.** Every hard-key
route is untouched in its own right; the only navigational change to an EXISTING route is that
`TODAY` moved from a hard key to a button one tap into `DASHBOARD`.

## The two hands paths this branch adds, and the one gap it does NOT close

**`WidgetPagerRoot(onOpenRoute: (String) -> Unit)`** is the new seam - the pager reaches outside
itself the same way every other top-level screen in this app's `NavHost` already does (a plain
callback up to `LegionShell`, which calls `navController.navigate`), never by owning its own
`NavHostController`. Two callers wired this branch:

1. **The HOME page's "CLASSIC" button** (only rendered on page 0) - `onOpenRoute(LegionRoute.TODAY)`.
   Named CLASSIC because it is genuinely the old Today panel, unmodified, carrying capabilities the
   seeded HOME arrangement does not yet replicate: the ALERTS pane (quarantined-file count, tap-
   through to Money), the Gemini-key advisory row, and the media mini-bar's own tap-through to the
   Spotify panel. `DefaultArrangementSeeder`'s own doc comment already named TODAY -> HOME as its
   mapping target; this button is the honest acknowledgment that the mapping is not yet 1:1.
2. **Each aspect page's "OPEN FULL SCREEN" button**, present only when `legacyRouteForAspect(aspect
   .name)` resolves - a plain `when` keyed against the exact `ASPECT_NAME` string literal each of
   `engine/fleet/FleetAspectSeeder.kt`/`engine/ledger/LedgerAspectSeeder.kt`/
   `engine/pantry/PantryAspectSeeder.kt`/`engine/notes/NotesAspectSeeder.kt`/
   `engine/places/PlacesAspectSeeder.kt` seeds (`Fleet`/`Ledger`/`Pantry`/`Notes`/`Places` ->
   `FLEET`/`MONEY`/`MONEY_PANTRY`/`NOTES`/`FLEET_PLACES`), pinned by `LegionRouteTest`'s own test
   against those seeders' real constants rather than a second, hand-typed copy of the strings. This
   is the hands path to capabilities the generic engine widgets do not yet carry - statement/receipt
   ingestion, the OBD live views, settings screens embedded in the legacy Fleet/Notes/Ledger
   screens.

**The Dates aspect and any user-created aspect carry no such button, correctly** - `Dates` is
genuinely new (CLAUDE.md §10/ticket 19: it never had a pre-existing legacy screen to link to, so
this is not a capability the cutover removed), and a driver-created aspect from the pager's own "+"
page never had one either.

**A gap this branch did NOT introduce, found while building it, and explicitly out of this
branch's scope: no engine widget navigates anywhere on tap.** `RecordListWidget`/`StatTileWidget`/
`AgendaWidget`/`SingleRecordCardWidget`/`ChartWidget` (`ui/widgets/EngineWidgets.kt`) are all
read-only renders with zero `onClick`/`clickable` in the file (grep-confirmed), and `QUICK_ADD`'s
own `onAdd` callback is a literal no-op with a comment pointing at
`ui/generated/GeneratedFormScreen.kt` as the intended destination - unchanged by this branch.
`GeneratedListScreen`/`GeneratedDetailScreen`/`GeneratedFormScreen` (ticket 10's own "already
built" generated screens) are real, working composables, but grep across `app/src/main` shows
**zero live callers wire them into any `NavHost`** - the only place they are ever mounted today is
`GeneratedScreensScreenshotTest`, over a bare `ComponentActivity`. This was already true before
this branch (`WidgetPagerActivity` never wired them either), so it is not a regression this cutover
caused, but it IS the reason the aspect pages' own widgets cannot yet be each aspect's ONLY
drilldown path - the "OPEN FULL SCREEN" button above is what actually carries that weight today.
**Genuinely owed, named rather than silently worked around**: a follow-up ticket to give the
generated screens typed nav routes (`records/{recordTypeId}`, `records/{recordTypeId}/{recordId}`)
and wire `RECORD_LIST`/`SINGLE_RECORD_CARD`/`QUICK_ADD` taps through them. Out of scope here because
it is a nav-argument shape `LegionRoute.kt`'s own doc comment says this file has never needed before
("nothing here takes a navigation argument") - a real design decision, not a quick patch, and
exactly the kind of unscoped touch CLAUDE.md's working model asks an executing agent to stop and
surface rather than improvise.

## Default arrangements beyond HOME - deliberately not extended this branch

`DefaultArrangementSeeder.seedHomeIfEmpty` seeds only the HOME page (`aspectId = null`); none of the
five real aspect pages (Fleet/Ledger/Pantry/Notes/Places) get a seeded arrangement, so a fresh
device's aspect pages read "NOTHING PLACED ON THIS PAGE YET" until a driver places a widget by
hand. **Deliberately not extended in this branch**, for two reasons stated rather than assumed
away: first, a reasonable per-aspect seed needs a real `FieldDef`/`RecordType` id to point a
`STAT_TILE`/`RECORD_LIST` at, and guessing one risks seeding a widget that reads as authoritative
over a field nobody chose (the same "not configured yet, in words" discipline the HOME seed's own
doc comment already holds itself to for `STAT_TILE`/`QUICK_ADD`); second, every aspect page already
has a real, working fallback today - the "OPEN FULL SCREEN" button this branch adds. The empty
state is honest, not broken: it says nothing has been placed, because nothing has, and one tap away
is the exact same full-capability screen that page's tab used to be. Extending the seeder with real
per-aspect defaults (mirroring `TODAY`'s BIO/CRED/FLEET/LOG half-tile row, ticket 08's own answer)
is a named follow-up, not a silent gap.

## Postscript, 2026-08-25: reverted after a night of real use

**Kevin's own arc on this cutover, stated plainly rather than smoothed over**: "i like it" on
first look at the pager as HOME, then - after actually living with it overnight on the A25 -
"home screen > kill it, revert everything to classic." Both were genuine reactions at the time
they were said; the second is the one that governs. This is not a case of the first cutover being
wrong on arrival - the pager, its eight widget kinds, `DeckGrid`'s edit mode, and the per-aspect
pages all worked exactly as built and went through seven on-device grid-feel rounds before this
branch ever flipped HOME onto them. What field use showed is narrower: as an every-open HOME
surface, seeded arrangements read thinner than the old `TodayScreen` panel they were modelled on
(this doc's own "Default arrangements beyond HOME" section named that gap at the time, and it is
the gap Kevin felt).

**The revert, same shape as the flip itself - a route-table change, not a deletion.**
`LegionRoute.TODAY` is `NavHost`'s `startDestination` and the HOME hard key's target again, exactly
the pre-cutover-5 shape this doc's own "before" column recorded. `LegionRoute.DASHBOARD` (the
pager) is NOT deleted and NOT code-orphaned: it stays a real, reachable `composable` destination,
demoted from HOME/hard-key/start-destination down to a single **"DASHBOARD" button on
`TodayScreen`** (ui/TodayScreen.kt (deleted 2026-09-01, one-today ticket 07), a lone row at the top of the agenda list, deliberately not
inside the HERO pane's own whole-pane click target) - the mirror image of the "CLASSIC" button this
cutover added to the pager's HOME page, which is now removed as pointless (TODAY is home again, one
tap - or the back button - away from anyone who reaches the pager at all). This keeps the pager a
real hands path (ADR 0035) to the aspect engine's generic widgets rather than orphaning the seven
on-device rounds it went through.

**The aspect-add bug, found while reverting, was real and is now fixed.** Kevin also reported
"adding an aspect doesn't work." Tracing it: this cutover's own "Cleanup" section never mentioned
the pager's own "+" page because that page was untouched by the home flip - the bug predates this
branch and was simply surfaced by using the app. `AddAspectPage` (`ui/widgets/WidgetPagerScreen.kt`)
was exactly the stub ticket 18's own report named it as ("stub screen is fine this pass"): it wrote
a bare `Aspect` row and NOTHING else - no `RecordType`, no `FieldDef`. A driver who tapped CREATE
got a new page that would read "NOTHING PLACED ON THIS PAGE YET" forever, because every write tool
(`create_record`, `describe_aspect`, every `WidgetKind`) keys off a record type id, and none
existed. The aspect looked created; nothing about it was usable. Fixed by giving the form a starter
record type name and one-or-two starter field names, committed through
`EngineToolbox.manualCreateDraft` + `EngineToolbox.commitCreateAspect` - the exact same write path
the voice `create_aspect` tool's confirm handshake commits a Pro-drafted schema through, so this is
one implementation of "aspect + record type + fields land in Room," not a second one that could
drift from it.

**Screenshot baseline re-recorded, one file, one deliberate diff**: `pager-home-seeded-arrangement.png`
- the header row lost the "CLASSIC" button (now reads only "EDIT"), nothing else in the seeded HOME

`DASHBOARD` out; `topLevelOf`/`label` both flipped back). `./gradlew testDebugUnitTest -Pnokey` and
`./gradlew testDebugUnitTest verifyRoborazziDebug` (real key path) both green.
`python tools/voice_guide.py` exit 0, no drift (this revert touches no voice tool).
