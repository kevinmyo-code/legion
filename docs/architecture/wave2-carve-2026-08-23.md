# Wave 2 carve: pantry onto the engine

Owed by `.scratch/aspect-engine/issues/21-migration-waves.md` point 2 ("per-aspect carve... produced
per wave before its build starts") and ticket 11 answer point 5 (the per-plugin inventory table).
Written before any code in this wave, following [Wave 1's carve](wave1-carve-2026-08-23.md)'s own
shape and reusing its reasoning rather than repeating it.

## The finding that reshapes this carve: there is no quarantine state to migrate

CLAUDE.md §4/§5 v3 note both call out that every `PantryReceipt`/`PantryLineItem` row is
LLM-extracted by construction. Read to its leaf (`pantry/PantryReceiptAgent.kt`,
`pantry/PantryController.kt`), that construction is stronger than "no `ingestMethod` column" - **the
gate is enforced upstream of Room, not inside it.** `PantryReceiptAgent.parseAndReconcile` returns a
sealed `PantryIngestResult`: `Success` (money reconciled exactly against the receipt's own printed
subtotal/tax/total, per CLAUDE.md §4 rules 2 and 6) or `Quarantined` (a worded reason string, no
data). `PantryController.importReceipt` only ever calls `pantryReceiptDao().insert()` /
`pantryLineItemDao().insertAll()` inside the `Success` branch - a `Quarantined` result returns
straight back to the caller as a failed `PantryImportResult` and **nothing is written to Room at
all**. There is no `quarantined_receipts` table, no quarantine flag column, no soft-delete/tombstone
column on either entity (confirmed by reading `PantryReceipt.kt`, `PantryLineItem.kt`,
`PantryReceiptDao.kt`, `PantryLineItemDao.kt` in full - neither DAO exposes a delete or an
update). **Every row this migration will ever find already passed the gate by the time it reached
disk.** The only artifact of a quarantined attempt is the source photo, left in place on
`PantryPhotoStore` for the user to retry from - not a Room row, not this wave's concern.

Consequence for this wave: point 2's "if the legacy schema has quarantine state, quarantined rows
are NOT migrated as clean records" has no work to do here - there is no quarantine state IN the
schema to find. Provenance for every migrated row is unconditionally `RecordProvenance.LLM_RECONCILED`
(never `USER`, unlike Wave 1's notes/places copy, and never conditional on a per-row flag that does
not exist).

## The carve table

| Entity (table) | Live? | Carve | Reasoning |
|---|---|---|---|
| `PantryReceipt` (`pantry_receipts`) | Yes, primary | **Becomes the `Receipt` record type in a new `Pantry` aspect** | The reconciled receipt header - store, date, currency, printed total. |
| `PantryLineItem` (`pantry_line_items`) | Yes, primary | **Becomes the `LineItem` record type in the same `Pantry` aspect**, referencing `Receipt` | One line item per gated receipt row, plus the four LLM macro estimates. |
| `PantryPhotoStore` (filesystem, `pantry_receipts/` dir) | Yes, plugin-internal | **Stays plugin-internal - not migrated, not touched** | Ingestion-only staging: a photo lands here before extraction and is deleted on success (`PantryPhotoStore.delete`, called from `PantryController.importReceipt`'s `Success` branch) or kept on a quarantine for retry. By the time a `PantryReceipt` row exists to migrate, its own photo is almost always **already gone** - `PantryReceipt.sourceImagePath`'s own doc comment says exactly this: "kept as a text record of provenance, not a live reference." There is nothing live here for a migration to carry into `EnginePhotoStore` (the engine-native photo store `data/EnginePhotoStore.kt` already ships for `FieldType.PHOTO` on other record types) - only a path string, which the `Receipt.sourceImagePath` field below carries as-is. |
| `LedgerCurrency` (`SGD`/`USD` enum, shared with ledger) | Yes | **Not its own record type - becomes a `FieldType.CHOICE` field value on `Receipt`** | Same enum ledger already uses; the engine has no first-class currency type (`FieldConfig`'s vocabulary is TEXT/NUMBER/MONEY_CENTS/DATE/DATETIME/BOOLEAN/CHOICE/MULTI_SELECT_CHOICE/REFERENCE/PHOTO/LOCATION/RATING/COMPUTED, locked at ticket 03), so `CHOICE` with options `["SGD", "USD"]` is the closest fit and is what `RecordType`/`FieldDef`'s existing vocabulary offers. |

No entity here is "dead" the way `car_tasks`/`place_reminders` were in Wave 1 - pantry is a small,
young aspect (2026-07-31) with no prior absorption history to trace through.

## Field mapping: `PantryReceipt` -> Pantry aspect, `Receipt` record type

Owner plugin id: `"pantry"`. Locked+required: `store`, `purchaseDate`, `currency`, `total` - the
four facts the reconciliation gate itself verified or requires before a row can exist at all.
`sourceImagePath` is NOT required/locked (see reasoning below).

| `PantryReceipt` column | Field name | `FieldType` | Required/locked | Notes |
|---|---|---|---|---|
| `store` | `store` | TEXT | yes | |
| `purchaseDate` | `purchaseDate` | DATETIME | yes | **Not wired as `primaryDueDateFieldId`.** A past grocery purchase date is not an agenda-shaped "due" the way a Notes reminder or a Dates event is - promoting it would put every historical receipt into a cross-aspect agenda meant for upcoming, actionable items. Deliberate scope cut, stated rather than defaulted into. |
| `currency` | `currency` | CHOICE | yes | Options `["SGD", "USD"]` - `LedgerCurrency`'s own two values, duplicated as plain strings rather than a dependency on that enum, same "engine package never depends on a plugin package" reasoning `NotesAspectSeeder.REPEAT_KIND_OPTIONS`'s own doc comment states for `notes/RepeatKind`. |
| `totalCents` | `total` | MONEY_CENTS | yes | **Wired as `primaryAmountFieldId`** - the receipt's own printed, gate-verified total is exactly the "the standard set" promotion ticket 03 answer point 1 describes; a spend-across-aspects query can read `EngineRecord.amountCents` without touching payload JSON. First seeder in the repo to set this column (Notes/Places wired `primaryDueDateFieldId` only); same update-if-changed idempotent shape, mirrored from `NotesAspectSeeder.ensureSeeded`'s own `primaryDueDateFieldId` block. |
| `sourceImagePath` | `sourceImagePath` | TEXT | no, not locked | Deliberately plain TEXT, not `FieldType.PHOTO` - a `PHOTO` field (per `data/EnginePhotoStore.kt`'s own doc comment, "the record's own permanent data, kept for the record's whole lifetime") implies a live file this record owns; a migrated `sourceImagePath` is, per that column's own doc comment, usually already deleted. Storing it as TEXT keeps the provenance string (matches the legacy column's own stated purpose - "a text record of provenance, not a live reference") without implying a photo picker UI should try to render a file that in the overwhelming case does not exist. Not required/locked because a future user-authored Pantry receipt (post-cutover, hand-entered) has no photo to point at at all. |
| `syncId` | - | - | - | Reused directly as the migrated record's `guid` - see identity section below, same shape as Wave 1's `ListItem.syncId` reuse. |
| `id` | - | - | - | Not carried as a field. Its ENGINE identity (the new `EngineRecord.id`) is what `LineItem.receipt` below references - see the copier's own doc comment for why line items must be copied strictly after their receipt. |

## Field mapping: `PantryLineItem` -> Pantry aspect, `LineItem` record type

Owner plugin id: `"pantry"`. Locked+required: `receipt`, `name`, `quantity`, `totalPrice` - the
fields present on every gate-reconciled row. The four macro fields are estimates by construction
(CLAUDE.md §4 rule 5) and are named with an `estimated` prefix rather than described as one, because
**`FieldDef` carries no separate description column** (confirmed by reading `FieldDef.kt` in
full) - `ui/generated/GeneratedFormScreen.kt:148` renders `fd.name` directly as the field's on-screen
label (`fd.name + if (fd.required) " *" else ""`), so the field NAME is the only user-facing string
this schema layer has, and it is the one CLAUDE.md §4 rule 5 requires to say "estimate."

| `PantryLineItem` column | Field name | `FieldType` | Required/locked | Notes |
|---|---|---|---|---|
| `receiptId` | `receipt` | REFERENCE | yes | Targets the `Receipt` record type, **`DeletePolicy.CASCADE`** - deleting a receipt is meant to remove its line items with it (a line item with no receipt is meaningless data, unlike, say, a `NULLIFY`-policy optional link). This is the wave's one genuinely new engine-schema shape: no prior wave declared a `REFERENCE` field ([`RecordStoreTest`](../../app/src/test/java/com/kevin/legion/engine/RecordStoreTest.kt) exercises `REFERENCE`/`CASCADE` against hand-built test schemas only; this is the first REAL aspect to use it). |
| `name` | `name` | TEXT | yes | |
| `quantity` | `quantity` | NUMBER | yes | Every legacy row carries a non-null quantity (Kotlin default `1.0`), so required is correct, not merely convenient. |
| `unitPriceCents` | `unitPrice` | MONEY_CENTS | no | Legitimately absent on many receipts (a line with no printed unit price, only a line total). |
| `totalPriceCents` | `totalPrice` | MONEY_CENTS | yes | **Wired as `primaryAmountFieldId`** on `LineItem` - this is the figure the gate itself verified (`sum(items) == subtotal`), so it is exactly the promotable "amount" for this record type. |
| `caloriesKcal` | `estimatedCaloriesKcal` | NUMBER | no | ESTIMATE - see this section's header note. |
| `proteinG` | `estimatedProteinG` | NUMBER | no | ESTIMATE. |
| `carbsG` | `estimatedCarbsG` | NUMBER | no | ESTIMATE. |
| `fatG` | `estimatedFatG` | NUMBER | no | ESTIMATE. |
| `syncId` | - | - | - | Reused directly as the migrated record's `guid` - see identity section below. |
| `id`/`receiptId` (legacy FK value) | - | - | - | Not carried as data; used only to look up the ALREADY-migrated parent's new `EngineRecord.id` at copy time (see copier doc comment). |

No `DURATION` field type was needed; 13 of the (deferred) 14 `FieldType` values are enough (every one
except `LOCATION`, `RATING`, and `COMPUTED`, none of which pantry needs).

## Reconciliation status, quarantine, and provenance

- **Provenance is unconditionally `RecordProvenance.LLM_RECONCILED`** for every `Receipt` and every
  `LineItem` this migration writes - never `USER`, never conditional on inspecting any column,
  because (per the finding above) there is no other kind of row this table can hold. This is
  CLAUDE.md §5's v3 note ("every row is LLM-extracted by construction") carried forward literally:
  the migration does not RE-DERIVE provenance, it STATES what was already true before the row ever
  reached Room.
- **Money is carried as `Long` cents, unchanged, at every step** - `totalCents`/`unitPriceCents`/
  `totalPriceCents` copy straight through with no floating-point conversion, matching CLAUDE.md §4
  rule 3.
- **Macro estimate fields are copied verbatim, never re-verified** - they were never part of the
  gate to begin with (CLAUDE.md §4 rule 5), and this migration does not invent a check that never
  existed.
- **No quarantine state exists to exclude** - see the finding above. Stated explicitly, not silently
  assumed, per instruction 2's own requirement to say what was found.

## What the copier does and does not copy

- **Copies every `PantryReceipt` row, unconditionally** (there is no `deleted` column to filter on,
  unlike Wave 1's `ListItem`/`TaggedPlace` - see the carve finding above), via a new
  `PantryReceiptDao.getAll()` query (an additive `@Query`, no schema/version change - it reads the
  same columns `getRecent`/`getAllForCharts` already expose, just without a `LIMIT` or a narrowed
  projection).
- **Copies every `PantryLineItem` STRICTLY AFTER its own receipt has been copied** - a `LineItem`'s
  `receipt` field is a live `FieldType.REFERENCE`, and `RecordStore.create`'s `validateReferences`
  step rejects any reference pointing at a record id that does not yet exist. The copier keeps a
  `legacyReceiptId -> newEngineRecordId` map built while copying receipts, and looks up each line
  item's parent through that map, in the SAME pass (`db.pantryLineItemDao().getForReceipt(receipt.id)`
  per receipt) rather than a single flat query across all line items - this also means a
  line item can never be orphaned mid-migration even if the process dies between a receipt and its
  items (see idempotency below).
- **Preserves timestamps exactly, in one atomic write**, same `RecordStore.create(now =, updatedAt =)`
  shape Wave 1's senior-review fix established - `PantryReceipt` carries no separate
  `createdAt`/`updatedAt` (it was never edited after insert, per its own DAO having no `update`
  method), so both clocks are seeded from `purchaseDate` for the receipt... **correction, resolved
  during implementation:** neither `PantryReceipt` nor `PantryLineItem` carries any insert-time
  clock at all - `purchaseDate` is a USER-STATED fact from the receipt (when the shopping happened),
  not a bookkeeping timestamp for when the row was written to Room. Using it as the engine record's
  `createdAt`/`updatedAt` is the closest available anchor and is what this migration does, stated
  here as a deliberate substitution rather than left implicit - a receipt logged today for a
  purchase two weeks ago will show a two-week-old `createdAt` on its engine record, which is correct
  for "when did this data become true" and not a bug.
- **Identity.** Both `PantryReceipt.syncId` and `PantryLineItem.syncId` already exist as stable,
  per-row UUIDs (present since v3, "for exactly this kind of cross-device identity purpose", same
  column Wave 1's `ListItem.syncId` reuse cites) - reused directly as each migrated record's `guid`.
  No `UUID.nameUUIDFromBytes` derivation was needed here (unlike Wave 1's `TaggedPlace`, which
  carried no identity column of its own) - stated so the choice reads as "the data already had a
  stable key" rather than "a key was invented."

## Voice tools: what stays, what the carve marks for cutover-time removal only

Per instruction 4: leave every existing tool working; nothing is removed, changed, or rewired in
this wave. Named here only as the inventory ticket 11 point 5 asks for, so cutover (a later wave)
knows what it is retiring:

| Tool (in `service/LiveToolbox.kt`) | Backs onto | Dies into a meta-tool at cutover? |
|---|---|---|
| `list_recent_groceries` | `PantryController.recentLineItemsWithCurrency` | Yes - `list_records` against the `LineItem` record type, joined through the `receipt` reference for currency |
| `get_grocery_spend` | `PantryController.totalSpendCentsByCurrency` | Yes - a `COMPUTED` `Aggregate` field (`SUM` over `Receipt.total`, grouped by `currency`) once the generic aggregate machinery supports a group-by, OR a small pantry-specific read over `EngineRecord.amountCents` - **not fully resolved here**, named as an open question for the cutover wave rather than answered speculatively |
| `import_receipt` | Opens the camera/gallery picker, then `PantryController.importReceipt` -> `PantryReceiptAgent.extract` | **No** - same reasoning as Wave 1's `AlarmScheduler` exception: the vision-extraction gate is native capability-plugin logic (camera intent, `SubAgent` vision call, the reconciliation math itself), not a generic CRUD verb a meta-tool could express. Only the record STORAGE moves to the engine at cutover; the ingestion pipeline (`PantryReceiptAgent`/`PantryPhotoStore`) stays a plugin, unchanged, and keeps writing through the OLD `PantryReceiptDao`/`PantryLineItemDao` tables until cutover explicitly re-points `PantryController.importReceipt` at `RecordStore.create` instead. |

## Owed follow-ups, named rather than silently dropped

1. **Cutover per aspect** (ticket 14 point 2) is explicitly NOT this wave's job. `pantry/`,
   `ui/PantryImportActivity`, and all three `LiveToolbox` pantry tools keep reading and writing the
   legacy `pantry_receipts`/`pantry_line_items` tables unchanged until this aspect is verified on the
   A25 and cut over in its own later commit.
2. **`get_grocery_spend`'s cutover shape is an open question**, named above rather than answered -
   the engine's `COMPUTED Aggregate` vocabulary (ticket 04) does not yet describe a group-by, and
   pantry's per-currency total is exactly that shape.
3. **Neither `PantryReceipt` nor `PantryLineItem` is dropped.** They stay exactly as they are today;
   this wave adds new tables' worth of DATA (rows in `aspects`/`record_types`/`field_defs`/
   `records`), not a schema change to any existing table - matching Wave 1's own closing note.
4. **`PantryReceiptDao.getAll()` is new** (this wave adds it) but is a plain additive `@Query`, not a
   Room schema change - no migration, no version bump, no `app/schemas/` diff.
