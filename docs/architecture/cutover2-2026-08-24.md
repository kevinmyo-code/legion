# Cutover 2: Pantry becomes engine-native

Owed by `.scratch/aspect-engine/issues/22-cutover-per-aspect.md` ("Cutover per aspect: the engine
becomes the read and write path"), open question 2 ("Pantry: persist subtotal/tax/other so the
gate invariant is re-checkable post-hoc"). Written before this doc's own author claims the branch
is done, per CLAUDE.md §8's L11 ("a ticket's own verification steps are gates, not notes") - same
discipline `cutover1-2026-08-24.md` set, and the worked example this doc follows rather than
re-deriving its own shape from scratch.

**The reconciliation gate (CLAUDE.md §4) is UNCHANGED and applies harder here than it did to
cutover 1.** Every `PantryReceipt`/`PantryLineItem` row is `RecordProvenance.LLM_RECONCILED`,
never `USER` - this is document-extracted data, gated before it ever reaches Room
(`docs/architecture/wave2-carve-2026-08-23.md`'s own finding: "the gate is enforced upstream of
Room, not inside it"). Cutover does not touch `PantryReceiptAgent.parseAndReconcile` at all - the
gate's arithmetic, its quarantine messages, and its "nothing partial is ever written" posture are
byte-for-byte identical to the pre-cutover code. What cutover changes is only WHERE a gate-passed
`Success` result lands.

## What "cutover" means here, precisely

Before this branch: the engine held a COPY of every `PantryReceipt`/`PantryLineItem` (wave 2), but
nothing read or wrote it - `PantryController` was still 100% legacy-table-backed, and the engine
copy was write-once, dead weight, exactly like wave 1's notes/places before cutover 1.

After this branch: `PantryController` is internally engine-backed (every read and write goes
through `RecordStore` against the Pantry aspect's `Receipt`/`LineItem` record types), and every
caller - `ui/PantryScreen.kt`, `service/LiveToolbox.kt`'s `list_recent_groceries`/
`get_grocery_spend` - keeps calling the SAME public functions on `PantryController`, unchanged
(ADR 0035: "the controller keeps its seam"). The legacy `pantry_receipts`/`pantry_line_items`
tables are **frozen for new content** - every receipt imported from this branch forward is written
through the engine, never the legacy DAO.

## What died

Nothing was deleted. `PantryReceipt`/`PantryLineItem` entities, their DAOs, and every existing
column stay exactly as they are - this cutover adds new engine SCHEMA (three `FieldDef` rows on
the `Receipt` record type) and rewires one controller's internals, nothing more. Matches wave 2's
own closing note and cutover 1's "nothing was deleted in this pass."

## The bridge: how the controller keeps its seam

Every public `PantryController` function keeps its exact pre-cutover signature and return type
(`PantryReceipt`/`PantryLineItem`/`PantryCurrencyTotal`/`PantryReceiptSummary` - the legacy Room
row shapes), so every caller flips with zero changes of its own. What changed is entirely internal:

- `PantryController` resolves the Pantry aspect schema (`PantryAspectSeeder.ensureSeeded`),
  converts every `EngineRecord` it reads into an in-memory `PantryReceipt`/`PantryLineItem`
  (`toReceipt`/`toLineItem`, reusing `wave2-carve-2026-08-23.md`'s exact field mapping - not a
  second mapping), and writes through `RecordStore.create`.
- **`importReceipt`'s gate boundary is exactly where it always was.** `PantryReceiptAgent.extract`/
  `parseAndReconcile` are untouched. A `PantryIngestResult.Quarantined` returns straight back with
  no engine call at all - the gate still writes NOTHING on a quarantine, same as before cutover.
- **`importReceipt` delegates a `Success` result to `writeReceipt`, its own network-free half**
  (mirrors `PantryReceiptAgent.parseAndReconcile`'s "network-free... unit-tested directly" split -
  `PantryControllerTest` calls `writeReceipt` directly with a hand-built `Success`, no Gemini key or
  network needed). `writeReceipt` writes receipt-then-items inside one `androidx.room.withTransaction` block,
  same primitive `ledger/IngestPipeline.kt`/`ledger/LedgerController.kt` already use elsewhere in
  this codebase. The receipt is created first (its engine id is required by every line item's
  `REFERENCE` field - `RecordStore.create`'s reference-validation step rejects a reference to an
  id that doesn't exist yet, same ordering constraint the wave-2 copier itself already documented).
  Any `RecordStore.WriteResult.Failure` - on the receipt OR any line item - throws a private
  `EngineWriteFailedException` that `withTransaction` catches to roll back the WHOLE write, so a
  receipt can never be left with some but not all of its line items. `writeReceipt` then reports a
  worded failure ("checked out, but I couldn't save it") rather than a false success - CLAUDE.md
  §7's outcome-verb rule, applied from the first line of this rewrite rather than retrofitted after
  a senior review found it missing (cutover 1's should-fix 3).
- **`recentLineItems`/`recentLineItemsWithCurrency`/`recentReceiptsWithItems` re-derive the old SQL
  `JOIN ... ORDER BY purchaseDate DESC LIMIT` in memory** - reading every active engine record for
  the aspect and sorting/capping in Kotlin, same "personal household app's data volume, not an
  enterprise table scan" tradeoff `RecordStore`'s own class doc already accepts for its aggregate
  scans, and the same one CLAUDE.md §10 already accepted for the untested pre-cutover DB-write
  paths this replaces.

## Anchor persistence (the owed wave-2 follow-up, ticket 22 open question 2)

`PantryReceiptAgent.parseAndReconcile` already reads `subtotal`/`tax`/`otherCharges` off the
receipt's own print and reconciles against them - before this branch, that arithmetic's INPUTS were
thrown away the instant a receipt was written, so nothing later could re-derive "did this actually
tie out" without re-running the whole extraction.

1. **`PantryIngestResult.Success`** gained three new nullable fields - `subtotalCents`, `taxCents`,
   `otherChargesCents` - populated directly from the same local `val`s
   `PantryReceiptAgent.parseAndReconcile` already computed for its own gate check. Not re-derived,
   not re-verified - carried straight through.
2. **`PantryAspectSeeder`** gained three new optional `MONEY_CENTS` fields on the `Receipt` record
   type (`FIELD_SUBTOTAL`/`FIELD_TAX`/`FIELD_OTHER_CHARGES`), added via the SAME idempotent
   `ensureField` path every other field in that seeder uses - additive schema DATA (new
   `field_defs` rows), not a Room migration, no `app/schemas/` diff, reaching Kevin's
   already-seeded phone the next time `ensureSeeded` runs (exactly the benefit the engine is
   designed to provide - see `NotesController`'s own `loggedAt` precedent from cutover 1).
   `PantryAspectSeederTest`'s field-count assertion updated 5 -> 8.
3. **`PantryController.importReceipt`** writes all three into the receipt's `fieldValues` map
   alongside the five wave-2 fields.
4. **Not required, not locked.** A receipt legitimately prints no subtotal/tax line (the
   tax-free-basket branch `PantryReceiptAgent`'s own doc comment names - Singapore GST-inclusive
   receipts) - null there means "not printed," never "not checked," since the gate already ran
   either way before the row could exist at all.
5. **Historical rows stay anchor-less - not backfilled.** Neither `PantryReceipt` nor
   `PantryLineItem` (the legacy Room entities) ever carried these three columns, so
   `EngineDataMigrationWave2`'s copier has nothing to read them FROM - a migrated row's three
   anchor fields are explicit JSON `null` (the field exists in schema, the value was never known).
   This is honest, not a gap: fabricating a subtotal for a receipt imported before this branch
   existed would assert a fact nobody verified. Stated here per instruction 3's own requirement,
   not silently left implicit.

## Catch-up (point 4)

`EngineDataMigrationWave2.catchUpOnce(context)`, same shape as
`EngineDataMigrationWave1.catchUpOnce`:

1. Guarded by its own SharedPreferences marker (`cutover2_pantry_catchup_v1_completed`) - runs at
   most once ever, called from `MidnightApplication.onCreate` in the SAME coroutine as, and
   immediately after, the ordinary wave-2 `copyPantryIfNeeded` call.
2. Clears `KEY_PANTRY_COMPLETED` (the ordinary fast-path skip `copyPantryIfNeeded` would otherwise
   take), then re-runs it. Its own per-row `guid` check (unchanged, and unaffected by the three new
   anchor fields - `RecordStore.create`'s reference/idempotency logic doesn't care how many
   optional fields a record type has) makes this an actual rescan: any row already copied is
   recognized and skipped, any row written to `pantry_receipts`/`pantry_line_items` between wave 2
   landing and this cutover install is picked up for the first time.
3. **No rekey pass needed - checked, not assumed.** Cutover 1 needed to rekey `ListItemSkip.itemId`
   because that column stored a legacy `list_items.id` directly. Grepped this codebase for anything
   analogous keying off a legacy `PantryReceipt.id`/`PantryLineItem.id`: nothing found.
   `data/PantryPhotoStore.kt` - the only other pantry-adjacent piece of state - is keyed by a
   save-time millisecond filename (`"${System.currentTimeMillis()}.jpg"`), never by a receipt row
   id, confirmed by reading the whole 39-line file. Stated as a finding, not silently assumed.
