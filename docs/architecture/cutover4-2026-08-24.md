# Cutover 4: Fleet becomes engine-native

Owed by `.scratch/aspect-engine/issues/22-cutover-per-aspect.md` ("Cutover per aspect: the engine
becomes the read and write path"). Written before this doc's own author claims the branch is done,
per CLAUDE.md §8's L11 ("a ticket's own verification steps are gates, not notes") - the same
discipline `cutover1-2026-08-24.md`/`cutover2-2026-08-24.md`/`cutover3-2026-08-24.md` set, and the
worked example this doc follows rather than re-deriving its own shape from scratch.

**This is the largest of the four cutovers** - fleet is the widest tool/screen surface of the arc
(28 voice tools per `docs/architecture/tool-inventory-2026-08-23.md`, plus `ui/FleetScreen.kt`,
`ui/TodayScreen.kt`, two hands-path write-dispatch files, three digest builders, one advisor
proposal executor, and a spend controller). **This is also the cutover that finally lands ticket
29's unification** - `.scratch/hands-and-senses/issues/29-one-source-for-service-history.md`'s
diagnosis ("service history and maintenance clock should be tied together as one object... that's
why there's the bug") was already schema-level-fixed by Wave 4's carve
(`docs/architecture/wave4-carve-2026-08-23.md`); this branch is what makes the LIVE APP actually
read and write through that unified schema instead of the split legacy tables the bug lived in.

## Scope, stated up front (matching Wave 4's own scope cut)

**This branch cuts over the core chain only: `vehicles`, `service_records`, `maintenance_items`.**
Every entity Wave 4's carve deferred to a follow-up wave - `BuildEntry`, `VehicleSpec`,
`OilAnalysis`, `MonthlyRecap`, `DailyDriveLog`, `YearlyWrapped`, `Drive` - stays legacy-backed here
too, unchanged, for the identical reasons that carve already gave. `OdbSample`/`CodeEvent`/
`CodeClearEvent`/`VehicleCapability`/`DriveReassignment`/`ChassisQuirk`/`ForesightNote` stay
plugin-internal permanently, per instruction 4 of this cutover's own brief ("OBD-live state,
telemetry, capabilities etc. stay plugin-internal... the OBD stack keeps writing its own tables
untouched").

## Senior review, 2026-08-24: one blocking finding, one should-fix (both taken)

**BLOCKING - `FleetRecordBridge.projectAnchor` fabricated joint facts.** The first version of this
function took the highest mileage across every `ServiceHistory` row for a service and the latest
date across every row INDEPENDENTLY, so a mileage from one row could pair with a date from a
completely different row - a joint (mileage, date) fact no single write ever actually stated
together. `VehicleController.mergeBackfillAnchors`'s own doc comment already names this exact
failure shape as forbidden ("pairing it with the fresh mileage would assert a fact nobody stated").
**Fixed**: `projectAnchor` now derives the anchor from a SINGLE row - the most-recently-stated one
(greatest `EngineRecord.updatedAt`) among `OBSERVED`+`ASSERTED` for that service - taking BOTH axes
together from that one row, including its nulls. This mirrors the legacy schema exactly:
`MaintenanceItemDao.setAnchor` always overwrote both anchor columns in one UPDATE, so the row's live
state was always whatever the LAST write fully stated, never a blend of two different writes' own
fields. See `FleetRecordBridge.projectAnchor`'s own doc comment for the full reasoning, and "The
unification" section below for what this changes in practice. New/updated tests:
`FleetEngineStoreTest`'s `an OBSERVED insert that matches only ONE axis of the ASSERTED anchor does
NOT supersede it - the both-axes rule` now also asserts the derived anchor is the most-recent row's
own two axes, never a blend; `the derived anchor's date is null when the most-recently-stated row is
dateless, even though an older row has a real date` is new, pinning the null-not-borrowed case
directly.

**SHOULD-FIX - `MonthlyRecapController`'s spoken/rendered service count read as complete when it
is not.** `serviceCount` still reads the legacy `service_records` table (this doc's own ruling
table already named this as a deliberate, deferred exception - `MonthlyRecap` itself is one of Wave
4's own deferred entities), but every surface that showed the bare number read as a complete count
with nothing telling the reader otherwise. **Fixed**: the two render sites
(`ui/fleet/FleetDrilldowns.kt:1013,1041`) and the narrative string
(`vehicle/MonthlyRecapController.kt:197`) now state in words that the figure may not include recent
services, until `MonthlyRecap` gets its own follow-up-wave cutover (ticket 23's own tracking item).

## The Vehicle mirror - a genuine fork, resolved and stated in words

Wave 4's carve deliberately did NOT carry `obdMac` as a field on the engine `Vehicle` record type -
its guid is derived from `obdMac` via a one-way hash (`FleetRecordBridge.vehicleGuid`,
`UUID.nameUUIDFromBytes`), so the engine record can be looked up FROM an obdMac string, but there is
no way to enumerate every registered car's `obdMac` FROM the engine payload alone - the hash cannot
be inverted. Seven more columns (`personaPrompt`/`voiceName`/`personaTraits`/`archived`/`onboarded`/
`lastOdometerPromptAt`/`tripMilesSinceBaseline`) were also deliberately left uncarried, per that same
carve's field-mapping table.

`getAll()`/`getAllIncludingArchived()` genuinely need every car's `obdMac`. `TelemetryRecorder.run`
(the single highest-frequency writer of anything fleet-related, once per 30 seconds while driving)
genuinely needs a legacy `vehicles` row to accumulate `tripMilesSinceBaseline` onto, per instruction
4's own "OBD-live state stays plugin-internal, keeps writing its own table."

**The resolution: `vehicle/FleetEngineStore.kt` is the ONLY writer of the legacy `vehicles` table's
identity columns, and it writes them ATOMICALLY alongside the engine record, every time.** Every
Vehicle-identity WRITE (`createVehicle`/`setIdentity`/`setEngine`/`applyDecodedIdentity`/
`setOdometerBaseline`) does both in one `db.withTransaction` block. Every Vehicle READ
(`getByMac`/`getAll`/`getAllIncludingArchived`) then serves straight from that always-in-sync
mirror - correct, because nothing else may write it, and it is the only place `obdMac` keys and the
seven uncarried columns can be read at all. `setArchived`/`markOdometerPrompted`/
`clearThisCarSentinel` touch ONLY the legacy-only columns, never identity - narrow, named,
single-purpose writers, not a second identity authority.

**This is not the same failure mode ticket 29 diagnosed.** Ticket 29's bug was two INDEPENDENTLY
writable stores of ONE FACT (a service's last-done mileage/date), each free to drift from the
other with nothing reconciling them. The Vehicle mirror is the OPPOSITE shape: ONE writer
(`FleetEngineStore`), touching two tables in the same transaction, for facts that are either
engine-authoritative (identity, mirrored down) or legacy-only-authoritative (telemetry, never
touched by the engine side at all). There is no second writer for either half to disagree with.
Vehicle identity was never split across two competing stores before this cutover either - unlike
service history, this was never the bug ticket 29 named, and this cutover does not reopen it as one.

## The unification: what actually changed, precisely

**Before this branch**: `ServiceRecord` (the events) and `MaintenanceItem.lastDoneMileage`/
`lastDoneDate` (the schedule's own clock) were two Room tables, and Wave 4's copier already unified
them into one `ServiceHistory` record type (`kind = OBSERVED`/`ASSERTED`) - but nothing LIVE read or
wrote that table yet. The schema fix existed; the drift kept happening in the tables the live app
actually touched.

**After this branch**: `MaintenanceItem.lastDoneMileage`/`lastDoneDate` no longer exist as a stored
value anywhere - `FleetRecordBridge.toMaintenanceItem`/`projectAnchor` DERIVE them, fresh, on every
read, from the SAME `ServiceHistory` rows (`OBSERVED` and `ASSERTED` alike) the service-history
screen and every voice answer also read. **There is no second place either figure could be left
stale**, because there is no second stored copy of either figure at all.

`projectAnchor`'s rule (senior review, 2026-08-24, MUST-FIX - the first version of this doc's own
justification below was factually wrong, and is corrected rather than quietly replaced): the anchor
is BOTH axes of the single MOST-RECENTLY-STATED `ServiceHistory` row for that service (greatest
`EngineRecord.updatedAt`), taken together, including a null. **The two axes may never come from
different rows.** The original version of this function took the highest mileage across ALL rows and
the latest date across ALL rows independently, which can pair a mileage from one row with a date
from a completely different one - a joint fact nobody ever actually stated in one write, exactly the
cross-fact pairing `VehicleController.mergeBackfillAnchors`'s own anti-pairing rule forbids ("pairing
it with the fresh mileage would assert a fact nobody stated"). The corrected rule mirrors the legacy
schema's real behaviour: `MaintenanceItemDao.setAnchor` always overwrote both anchor columns together
in one UPDATE, so the row's live state was always whatever the LAST write fully stated, never a
blend of two different writes' individual fields - selecting the single most-recently-updated
`ServiceHistory` row and taking both its fields wholesale reproduces that exact last-write-wins,
no-cross-write-blending contract over N rows instead of one mutable pair of columns.

**Due-ness implications for the Jeep's own shape, stated plainly.** The Jeep's real incident (a
dateless `ASSERTED` anchor at 227,483 mi, stated after a real 227,374-mile/12-Aug `OBSERVED` record)
migrates as two rows, neither superseding the other (the mileages disagree, so `explainedBy` is
false). Under the corrected single-row rule, whichever of the two was stated MOST RECENTLY (by
`updatedAt`) wins BOTH axes outright - if the `ASSERTED` anchor is the newer fact (the ordinary
case: a driver correction typically comes after the event it corrects), the derived anchor is
`(227,483 mi, null)` - the mileage axis is checkable against `intervalMiles`, the TIME axis reads as
unknown for this item until a dated write lands more recently, exactly matching what a legacy
single-row anchor would have shown after the SAME sequence of edits. This is a real, visible
narrowing versus the FIRST (buggy) version of this cutover, which would have shown `(227,483 mi,
12-Aug-dated)` - a due-ness figure on an axis nobody actually asserted together. The corrected
behaviour is the honest one: an unknown axis reads as unknown, not as borrowed certainty.

### ASSERTED-supersession, extended live (instruction 3)

Wave 4's own migration already had this rule for the ONE-TIME copy (`explainedBy`, the
both-axes-on-the-SAME-row correction from that carve's own senior review). This cutover adds the
LIVE version: `FleetEngineStore.insertObserved` - the one function EVERY real, precise "log a
service" write goes through, voice or hands - checks, in the SAME `db.withTransaction` as the
`OBSERVED` create, whether an `ASSERTED` row exists for the identical `(vehicleId, serviceName)`
pair (same deterministic guid the migration itself used, so a live write can supersede a MIGRATED
anchor exactly as readily as a live one). If every axis the `ASSERTED` row states agrees with the
new `OBSERVED` row on that SAME row - `FleetRecordBridge.explainedBy`, reused verbatim, not
reimplemented - the `ASSERTED` row is trashed in that same transaction. A real event that arrives
and explains a stated anchor makes the anchor's own separate existence redundant; a real event that
does NOT fully explain it (the Jeep's own dateless 227,483-mile anchor against a 227,374-mile/12-Aug
record) leaves both facts on file, stated as what they are, never silently reconciled - exactly
ticket 29's own instruction.

**Extended to the hands path too.** `ui/fleet/MaintenanceWrites.kt`'s `writeSetAnchor` DONE_AT-with-
cost addendum used to be a direct `ServiceRecordDao.insert` - a second writer, independent of
`logServiceDirect`'s own. It now calls the SAME `FleetEngineStore.insertObserved`, so a service
logged by hand on the ITEM DETAIL screen supersedes a matching `ASSERTED` anchor identically to one
logged by voice - the unification this cutover exists to land, extended to the supersession rule
itself, not just the read path. `FleetEngineStoreTest.kt`'s
`logServiceDirect through the voice path supersedes a matching ASSERTED anchor the SAME way` pins
this directly.

## Atomicity (instruction 8)

`FleetEngineStore.insertObserved` wraps the `OBSERVED` create and the `ASSERTED` supersession check
in one `db.withTransaction` block, `try`/`catch` OUTSIDE it (same primitive `ledger/IngestPipeline.kt`/
`pantry/PantryController.kt` already established) - `EngineWriteFailedException` thrown from either
step rolls the WHOLE transaction back. Two directions pinned:

- **Early failure**: a vehicle not on file (`engineVehicleId` resolves to null) fails before the
  transaction even opens, writing nothing - `insertObserved against a vehicle not on file fails
  with a worded reason and writes nothing`.
- **Both-halves-together**: a successful call leaves BOTH the new `OBSERVED` row AND the trashed
  `ASSERTED` row visible together, never one without the other - `a successful insertObserved
  leaves BOTH the OBSERVED create and the ASSERTED supersession applied together, never one
  without the other`. A genuine mid-transaction RecordStore failure on the supersession half (the
  `DeletePolicy.BLOCK` guard on `recordStore.delete`) is structurally unreachable today - nothing
  ever references a `ServiceHistory` row - so it is guarded defensively rather than independently
  fault-injected; stated as `reasoned`, not `tested`, in the assumptions ledger below.

`setAnchor`/`setNeverDone` (schedule-clock-clearing writes) also wrap their two-step writes
(neverDone flip + anchor write/clear) in one transaction each, same discipline.

## `DeletePolicy.BLOCK`, exercised live (instruction 2)

`FleetEngineStore.deleteVehicle` calls `RecordStore.delete` on the engine `Vehicle` record -
`ServiceHistory.vehicle`/`MaintenanceSchedule.vehicle` are both `DeletePolicy.BLOCK` references
(Wave 4's own field mapping, per instruction 1: "deleting a car with history should refuse, not
cascade silently"). `EngineDataMigrationWave4Test` already exercised BLOCK against MIGRATED data;
`FleetEngineStoreTest.kt` now exercises it against a LIVE write - `deleteVehicle on a car with live
ServiceHistory is BLOCKed, and nothing is written` / `...with a live MaintenanceSchedule (no
history yet) is also BLOCKed` / `...with neither history nor a schedule succeeds`.

**No live caller reaches `deleteVehicle` today.** Archive/unarchive (`FleetEngineStore.setArchived`)
is the only removal affordance this app currently exposes for a car - a hard-delete voice tool or
screen action does not exist, and this cutover does not add one (out of scope; no ticket
authorizes it). The refusal is real and worded (`DeleteResult.Blocked(blockers)`, every blocker
named), ready for whichever future surface calls it - stated so this is not mistaken for a wired,
user-reachable capability today.

## Catch-up (instruction 5)

**Checked, not assumed: Wave 4's own migration has no `catchUpOnce`, unlike Wave 1/2/3.**
`EngineDataMigrationWave4.kt` has exactly one entry point, `copyFleetIfNeeded`, guarded by a single
completion flag (`fleet_completed_v1`) plus the usual per-row `guid` backstop - there is no second,
reconciliation-shaped pass the way `EngineDataMigrationWave1/2/3.catchUpOnce` each have. Re-running
`copyFleetIfNeeded` is itself idempotent by construction (every row's `guid` is checked before any
write), so "re-run it once, idempotent" is satisfied by the EXISTING function - no new code was
needed or added for this instruction. Wave 4's own carve doc already named the one gap this leaves
open (owed-follow-up #8: an `ASSERTED` row computed once at copy time can go stale if a legacy
service is logged AFTER the copy but BEFORE this cutover installs) - **that gap is now closed by
this cutover landing at all**, not by a reconciliation pass: once `IngestPipeline`-shaped legacy
writes to `service_records`/`maintenance_items` stop happening (this branch's own ruling table:
zero writers), there is no more legacy-side drift for a catch-up pass to chase. The one remaining
window is between Wave 4's original copy and this cutover's install on a given phone - real, but
closed by installing this build, not by an additional migration step.

**No rekey pass needed - checked, not assumed**, same as cutover 2's own finding: nothing in this
codebase keys off a legacy `MaintenanceItem`/`ServiceRecord` row id (`ServiceRecord.id` is now
repurposed as the corresponding `EngineRecord.id` for a live-inserted `OBSERVED` row - see
`FleetRecordBridge.toServiceRecord`'s own doc comment - but nothing stored a legacy id anywhere
that would need remapping).
