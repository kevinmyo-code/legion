# Wave 1 carve: notes, lists, and places onto the engine

Owed by `.scratch/aspect-engine/issues/21-migration-waves.md` point 2 ("per-aspect carve...
produced per wave before its build starts") and ticket 11 answer point 5 (the per-plugin
inventory table, deferred to be enumerated per wave). Written before any code in this wave, per
that ticket's own instruction.

## The finding that reshapes this carve

**Notes and Lists are not two domains in the live code - they already collapsed into one, before
this map was ever charted.** `.scratch/notes-lists-calendar/` (a prior, separate effort) ran
`MIGRATION_9_10` and `MIGRATION_12_13`, which folded every named list and `CarTask` and
`PlaceReminder` into a single flat model: one `ItemList` row (`NotesController.theList`, "there is
exactly one... dissolve the car list. merge everything into one list model", Kevin 2026-08-11) and
every item a row in `ListItem` - checklist, note line, or reminder (time- or place-triggered) all
the same shape, distinguished only by which optional columns are populated. `car_tasks` and
`place_reminders` are **dead tables**: traced (`grep`, confirmed by reading `ReminderController.kt`
and `TelemetryRecorder.kt`) - nothing in live code writes a new row into either one anymore.
`car_tasks` gets nothing but a tombstone-purge sweep; `place_reminders` gets nothing but a stale
count read by `LogDigestBuilder` for a log line. Both tables stay in place (untouched, per this
wave's no-destructive-step rule) but are **not** a migration source - migrating them again would
either double-count content the `ItemList`/`ListItem` migration already carries, or copy rows a
prior migration already superseded.

This is not a contradiction of ticket 21's assumptions serious enough to block the wave (the
ticket authorizes exactly this kind of per-entity carve call: record type, plugin-internal, or
dies), but it changes the shape from "three aspects" to **two**: one **Notes** aspect absorbing
both notes and lists, one **Places** aspect. Flagged here in writing rather than silently decided.

Owner plugin id: `"places"`. All three fields locked+required - a place with no label or

| `latitude` | `latitude` | NUMBER | yes | |
| `longitude` | `longitude` | NUMBER | yes | |
| `timestamp` | - | - | - | Not its own field - used to seed `createdAt`/`updatedAt` on the copied `EngineRecord` (see migration copier), matching the "preserving timestamps" instruction. |
| `deleted` | - | - | - | Tombstoned (`deleted = 1`) rows are **not copied** - see "What the copier does not copy" below. |

No due-date field on this record type (a saved place carries no clock) - `primaryDueDateFieldId`
stays null, same as any record type with nothing date-shaped (`RecordType`'s own doc comment: "a
record type with no money-shaped or date-shaped field at all... simply never populates the
promoted column").

## What the copier does and does not copy

- **Copies:** every `ListItem` row `WHERE deleted = 0` (via `ListItemDao.allActive()`, which
  already reads across every legacy `ItemList` - matching the live app's own "one list" reality),
  and every `TaggedPlace` row `WHERE deleted = 0` (via `PlaceDao.getAll()`).
- **Does not copy tombstoned rows.** A `deleted = 1` row is already gone from every user-facing
  surface today; carrying it into the engine as a live OR a trashed `EngineRecord` adds fidelity
  nobody can observe, and the old table's own tombstone-GC sweep still reclaims it regardless of
  whether this wave ever ran. Stated as a deliberate scope cut, not an oversight.
- **Preserves timestamps exactly, in one atomic write.** `RecordStore.create` takes an explicit
  `updatedAt` parameter (defaulting to `now`, senior review 2026-08-23) precisely so a source row
  whose `createdAt` and `updatedAt` differ lands both in a SINGLE call - `now = source.createdAt`,
  `updatedAt = source.updatedAt`. The first cut of this copier used `create` then a conditional
  `update()` to bump `updatedAt` separately; that left a real crash window (a row could exist with
  `updatedAt == createdAt` forever if the process died between the two calls, and the per-row
  `guid` idempotency check would then treat it as "already copied" on every retry, freezing the
  wrong timestamp in place). A single call has no such window. `TaggedPlace` has only one clock
  column (`timestamp`), used for both, so its copier simply never passes `updatedAt` at all.
- **Provenance is `USER`** for every copied row, both aspects - every source row here was voice- or
  hand-entered, never document-extracted, so CLAUDE.md §4's reconciliation gate does not apply
  (same reasoning `CalendarImportController`'s own doc comment already states for its
  `DETERMINISTIC` rows: a straight field-by-field copy has no stated total to reconcile against;
  here it is not even an ingestion path at all, just a storage-location change for data the user
  already owns).
- **Identity.** `ListItem.syncId` is already a stable, per-row UUID minted for exactly this kind of
  cross-device identity purpose (`ListItem`'s own `syncId` column doc, same shape as
  `EngineRecord.guid`) - reused directly as the copied record's `guid`, so a Notes item's identity
  is unchanged by the copy. `TaggedPlace` carries no such column; its copied record's `guid` is
  derived deterministically from `label` (`UUID.nameUUIDFromBytes`), a real natural key rather than
  a fresh random UUID, so a second run of the copier (even one recovering from a mid-loop crash
  before the completion flag was set) can recognize and skip a row it already created instead of
  duplicating it - see the migration copier's own doc comment for the two-layer idempotency this
  buys.

## Voice tools: what stays, what the carve marks for cutover-time removal only

Per instruction 4: leave every existing tool working. Nothing is removed, changed, or rewired in
this wave. Named here only as the inventory ticket 11 point 5 deferred, so cutover (a later wave)
knows what it is retiring:

| Tool (in `service/LiveToolbox.kt`) | Backs onto | Dies into a meta-tool at cutover? |
|---|---|---|
| `add_item` / item-add family | `NotesController.addItem`/`addItemDue` | Yes - `create_record` against the Notes aspect |
| `manage_item` (tick/untick/remove/rename/etc.) | `NotesController.tick`/`untick`/`removeItem`/`renameItem` | Yes - `update_record`/`delete_record` |
| `set_reminder` | `ReminderController.add` (itself a thin wrapper over `NotesController`) | Yes - `create_record` with `triggerPlaceLabel` set |
| Place-tagging tools (`tag_place`/similar) | `PlaceController` | Yes - `create_record`/`update_record` against Places |
| `AlarmScheduler`-driven notification/missed-item surfaces | `notes/AlarmScheduler.kt` | **No** - alarm scheduling is native OS integration (`AlarmManager`), stays a plugin worker regardless of cutover; only the record STORAGE moves to the engine, the scheduling mechanism does not become a meta-tool. |

## Owed follow-ups, named rather than silently dropped

1. **Cutover per aspect** (ticket 14 point 2) is explicitly NOT this wave's job - old screens
   (ui/NotesScreen.kt (deleted 2026-09-05, one-today ticket 10 slice C - `ui/CalendarScreen.kt` is
   the Notes-aspect hands surface now), `ui/FleetScreen.kt`'s saved-places section) and old tools keep reading and
   writing the legacy tables until each is verified on the A25 and cut over in its own commit.
2. **Uniqueness on `label`** (Places) is not engine-enforced in v1 - flagged above, not blocking
   this wave since the old `PlaceController`/`PlaceDao.upsert` remains the live write path.
3. **`ItemList`/`CarTask`/`place_reminders` are not dropped.** They stay exactly as they are today;
   this wave adds new tables' worth of DATA (rows in `aspects`/`record_types`/`field_defs`/
   `records`), not a schema change to any existing table.

**Kevin ruled 2026-08-23: ONE aspect.** Notes and lists stay a single Notes aspect and a single pager page; widgets filter by field where a list-only view is wanted. The reviewer-flagged fork is closed.
