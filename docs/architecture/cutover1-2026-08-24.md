# Cutover 1: Notes and Places become engine-native

Owed by `.scratch/aspect-engine/issues/22-cutover-per-aspect.md` ("Cutover per aspect: the engine
becomes the read and write path"). This is the checklist a reviewer verifies branch
`feat/cutover1-notes-places` against - written before this doc's own author claims the branch is
done, per CLAUDE.md §8's L11 ("a ticket's own verification steps are gates, not notes").

**The reconciliation-gate/money rules (CLAUDE.md §4) do not apply to this wave** - every row here
is `RecordProvenance.USER` (hand/voice-entered), never document-extracted, same reasoning
`docs/architecture/wave1-carve-2026-08-23.md` already gives for the copier itself.

## What "cutover" means here, precisely

Before this branch: the engine held a COPY of every `ListItem`/`TaggedPlace` (wave 1), but nothing
read or wrote it - `NotesController`/`PlaceController` were still 100% legacy-table-backed, and the
engine copy was write-once, dead weight.

After this branch: `NotesController`/`PlaceController` are internally engine-backed (every read and
write goes through `RecordStore` against the Notes/Places aspects), and every caller - screens,
voice tools, digests, the recurrence engine, the goal-checklist sweep - keeps calling the SAME
public functions on those two objects, unchanged (ADR 0035: "the controller keeps its seam"). The
legacy `list_items`/`item_lists`/`places` tables are **frozen for new content** - every value a user
sees or acts on from this branch forward was written through the engine, never the legacy DAO.

## What died

Nothing was deleted in this pass. See "A genuine fork, surfaced rather than built" below for why
`tag_place`/`forget_place`/`read_list`/`manage_item` - the four LiveToolbox tools the tool-inventory
marks "dies into meta-tools (eventually)" - were deliberately NOT deleted here, contrary to a literal
reading of the dispatching brief's point 5.

## The bridge: how the controller keeps its seam

Every public `NotesController`/`PlaceController` function keeps its exact pre-cutover signature and
return type (`ListItem`/`TaggedPlace`), so every caller flips with zero changes of its own. What
changed is entirely internal:

- `NotesController` resolves the Notes aspect schema (`NotesAspectSeeder.ensureSeeded`), converts
  every `EngineRecord` it reads into an in-memory `ListItem` (`toListItem`, reusing
  `wave1-carve-2026-08-23.md`'s exact field mapping - not a second mapping), and writes through
  `RecordStore.create`/`update`/`delete`.
- `PlaceController` does the same against the Places aspect (`PlacesAspectSeeder`), converting to
  `TaggedPlace`.
- **`loggedAt` needed a new home.** Wave 1 deliberately did not carry `ListItem.loggedAt` onto the
  engine (it was `GoalChecklistSync`'s own sweep bookkeeping, not user content) - true only as long
  as the legacy table stayed live. This branch adds `FIELD_LOGGED_AT` to the SAME Notes `Item`
  record type (`NotesAspectSeeder`) - a new `FieldDef` row, not a Room migration, exactly the
  benefit the engine is designed to provide. `NotesAspectSeederTest` updated from 20 to 21 fields.
- **`ListItem.listId` is now cosmetic.** `ItemList` was never migrated (see above); every converted
  `ListItem` carries `listId = theList(context).id`, so every caller that ever compared
  `item.listId == list.id` (`GoalChecklistSync`, the `advisor/digest` builders) keeps working
  unchanged - there is still exactly one list, exactly as the live app already behaved before this
  wave.

## Catch-up design (point 3)

`EngineDataMigrationWave1.catchUpOnce(context)`:

1. Guarded by its own SharedPreferences marker (`cutover1_catchup_v1_completed`) - runs at most once
   ever, called from `MidnightApplication.onCreate` in the SAME coroutine as, and immediately after,
   the ordinary wave-1 `copyNotesIfNeeded`/`copyPlacesIfNeeded` calls (not a second, racing
   `appScope.launch` - see that file's own comment for why the ordering is deliberate).
2. Clears BOTH `KEY_NOTES_COMPLETED`/`KEY_PLACES_COMPLETED` flags (the ordinary fast-path skip those
   two functions would otherwise take), then re-runs `copyNotesIfNeeded`/`copyPlacesIfNeeded`. Their
   own per-row `guid` check (unchanged) makes this an actual rescan: any row already copied is
   recognized and skipped, any row written to `list_items`/`places` between wave 1 landing and this
   cutover install is picked up for the first time.
3. Runs `rekeySkipsToEngineIds` - walks every `ListItemSkip` row, looks up its legacy item's
   `syncId`, finds the matching `EngineRecord` by `getByGuid`, and re-points `itemId` at that
   record's id. A skip whose legacy item or matching engine record cannot be found is left alone
   (same accepted cost as wave 1's own "does not copy tombstoned rows" scope cut).
4. Only then sets the completion marker - a crash between the rescan and the rekey leaves the marker
   unset and the WHOLE catch-up (rescan included) retries next app start.

Verified: `EngineDataMigrationWave1CutoverTest` - a legacy row written after the first wave-1 pass
is picked up by `catchUpOnce`; a second `catchUpOnce` call is a no-op; a skip row keyed to a legacy
id is rekeyed onto its item's new, DIFFERENT engine id, and is no longer findable under the stale
one.

## Recurrence/skips (point 4)

`ListItemSkip.itemId` needed no schema change - see the `list_item_skips` row in the reader/writer
table above. Verified end to end: `NotesControllerTest`'s
`skipOccurrence keys ListItemSkip by the engine record id` writes a skip through the now-engine-backed
`NotesController.skipOccurrence` and reads it back by the engine id; `EngineDataMigrationWave1CutoverTest`
covers the historical rekey of a skip written before cutover.

## Reminders (point 6)

**Notes/place reminders were already NOT on `DatesAgenda`/`dueAt` before this branch, and still are
not after it - this is stated plainly rather than silently assumed.** `NotesAspectSeeder` wires
`startsAt` as the Notes `Item` record type's `primaryDueDateFieldId` (unchanged since wave 1), which
means a Notes item with a time trigger DOES populate `EngineRecord.dueAt` and DOES appear in
`DatesAgenda.windowed`'s cross-aspect query - that part was already true the moment wave 1 landed,
before any cutover. What this branch changes is narrower and different: the actual FIRING mechanism
(`AlarmManager`, via `notes/AlarmScheduler.kt`) now reads its candidate items from
`NotesController.allWithTimeTrigger`/`markMissed`/`setExactDowngraded` - engine-backed - instead of
`ListItemDao` directly, so a reminder set today keeps firing on schedule using the SAME OS-level
`AlarmManager` plumbing as before cutover. **No product behaviour changed here**: reminders fired
off `AlarmManager` before this branch and still do; what changed is which table the trigger data
underneath that alarm now lives in. `NotesControllerTest`/`EngineDataMigrationWave1CutoverTest`
exercise the read side; the actual `AlarmManager` schedule/fire cycle is unchanged code
(`AlarmScheduler.schedule`) and is not itself under test in this branch (it wasn't before, either -
it needs a real device clock/AlarmManager, out of Robolectric's reach) - **owed on-device**.

## A genuine fork, surfaced rather than built

The dispatching brief's point 5 said: "delete the dies-into-meta-tools notes/lists/places tools from
LiveToolbox per the inventory." Read literally, that means deleting `tag_place`, `forget_place`,
`read_list`, `manage_item` (the tool-inventory's own bucket) and letting the model fall through to
`EngineToolbox`'s nine generic meta-tools (`create_record`/`update_record`/`query_records`/etc.)
for Notes and Places.

**Traced end to end and stopped rather than built**, per CLAUDE.md's standing instruction to STOP
and surface a genuine product/architecture fork rather than improvise past it: `EngineToolbox` is
PURE generic `RecordStore` CRUD with no domain hooks at all. Deleting the four tools above and
routing solely through the meta-tools would silently drop, with no replacement:

- **Alarm scheduling.** `RecordStore.create`/`update` never call `AlarmScheduler` - a reminder
  created through `create_record` would never actually fire.
- **The recurring-item tick refusal** (`NotesController.tick`'s `repeatKind != null` guard, ticket
  04) - `update_record` would happily flip `done` on a recurring item.
- **At-most-one-trigger enforcement** (charting decision 4) - `update_record` writes a partial field
  set with no cross-field invariant at all.
- **Place-label normalization** ("home"/"work" synonyms, `PlaceController.normalizeLabel`) and the
  re-tag-upsert-by-label semantics this branch just added.
- **Missed-item bookkeeping** (`markMissed`/`dismissMissed`, ticket 12).

The wave 1 carve doc's own tool table already names the shape of this problem for one row -
"`AlarmScheduler`-driven notification/missed-item surfaces: No - alarm scheduling is native OS
integration... only the record STORAGE moves to the engine, the scheduling mechanism does not
become a meta-tool" - but does not extend that reasoning to the other three tools, which carry the
SAME kind of non-CRUD domain logic. **Ruling for this branch**: `tag_place`/`forget_place`/
`read_list`/`manage_item`/`set_reminder` all stay as LiveToolbox tools, rewired to call the (now
engine-backed) `NotesController`/`PlaceController`/`ReminderController` - satisfying "rewire the
surviving verbs to the controller" - but NOT deleted, since deleting them today would ship a real
regression the generic meta-tools cannot cover without a capability-plugin hook the engine does not
have yet (ticket 11's own "unbuilt API", named in CLAUDE.md §10). This is a decision for whoever
runs the meta-tool migration wave for Notes/Places specifically (mirroring how the wave 1 carve doc
already deferred the equivalent ledger/pantry/fleet calls to their own migration waves), not
something this cutover branch should decide unilaterally by deleting working reminders.

**PromptRoleNamingTest and VoiceGuideDataTest stay green because nothing in `LiveToolbox.kt`'s tool
declarations changed** - `python tools/voice_guide.py` ran clean (113 tools, no drift) with no
regenerated-file diff, confirming this.
