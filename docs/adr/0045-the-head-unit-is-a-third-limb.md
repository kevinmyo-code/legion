# 45. The head unit is a third limb, and the schema is what the limbs share

## Standing

**The MIDNIGHT_AI head-unit app is unfrozen and becomes a third limb of the Django engine**,
alongside the phone and the planned PWA. It stays in its own repository
(`github.com/kevinmyo-code/MIDNIGHT_AI`, package `com.kevin.midnightai`), on its own release
cadence, and reads the engine exactly as the phone does: HTTPS JSON, `Authorization: Token <key>`,
one device token of its own.

**What the limbs share is the engine's OpenAPI schema, not code.** `openapi/legion-schema.yaml` is
generated by `manage.py spectacular`, committed in this repo, vendored into each limb, and each
limb generates its own models from it. There is no shared Gradle module and no library artifact
between the repos.

Kevin, 2026-09-07: *"i want to add that too as a limb for the django app. it reads the django just
like ours"*, and on how the clients should be built, *"generate both clients from the OpenAPI
schema."*

**This reverses two rulings in CLAUDE.md**, and the matching edits land in the same commit as this
file:

- section 2's **phone-only** row. Phone-only is what killed the AOSP 8-10 ceiling, the
  frame-clock-only motion ban and the ADB blackout, and **none of those constraints come back** -
  they were constraints on LEGION's design, and LEGION's design is untouched here. What returns is
  narrower: a second Android app, which happens to run on a head unit, is a supported client of the
  engine.
- section 1's **"MIDNIGHT_AI is a FROZEN ARCHIVE... never build there"**. It is a live repository
  again. The half of that rule which survives is the half about provenance: LEGION's project
  history is still not written into MIDNIGHT_AI's memory files, and `memory/library/`'s FROZEN
  shelves are still frozen history about a dead commercial car-launcher product, not rules.

## Context

The head-unit app is the codebase LEGION was seeded from on 2026-07-31, so the two share class
names throughout and have diverged hard since - `GeminiLiveSession.kt` is 1337 lines there against
2790 here. That shared lineage is why sharing CODE between them is a trap and sharing a CONTRACT is
not: the two files have the same name and no longer have the same meaning, and any module factored
out to hold both would have to be re-diverged the first time either app needed a change the other
did not want.

The engine already published a schema, but it was **half a schema**. drf-spectacular silently drops
any `APIView` it cannot introspect, and it had dropped every hand-rolled one: `/api/events`,
every `/api/checklists/*` route, `/api/changes`, and all three auth endpoints appeared as bare paths
with untyped bodies, while `securitySchemes` was empty because nothing described
`DeviceTokenAuthentication`. Fifteen of the thirty-five types existed. A generated client built on
that would have been typed for the eight body tables and blind for exactly the two aspects the phone
already runs over Django. The gap was closed before any codegen was wired up
(`server/household/schema.py`, `api/errors.py`, and `extend_schema` on every hand-rolled view);
generation now reports zero errors and zero warnings.

## Consequences

**A schema that goes stale is worse than no schema.** Generated models still compile against an
outdated contract, so a field the server renamed arrives as `null` forever - nothing crashes and
nothing is logged. `tools/schema_check.py` regenerates and compares on every run of `/verify`, and
fails on drift. It also fails on any drf-spectacular warning, because a newly-untyped view is
dropped **silently** and would otherwise read as a clean pass with an endpoint quietly missing.

**Two vendored copies can skew.** The head unit's copy is a copy, and nothing enforces that it
matches this repo's. The checksum recorded in each repo's `openapi/README.md` is what makes the skew
visible to a human; it is deliberately not a build failure, because the limbs ship on separate
cadences and a head unit pinned to last month's contract is a legitimate state.

**Codegen stops at the models, and the transport stays hand-written in each limb.**
`EngineHttp`/`EngineFailure` sort every non-2xx into four branches, none of which a caller can
mistake for a success - CLAUDE.md section 7's outcome-verb rule expressed as a type rather than as a
convention. openapi-generator's `ApiClient` throws untyped exceptions, so generating the full client
would trade that guarantee for the code it saves. The head unit ports the design onto the OkHttp it
already has rather than importing Ktor.

**The head unit is a client, so section 4's gate does not move.** It reads what the engine already
gated and may not ingest anything on its own terms. Anything it wants to WRITE goes through a Django
endpoint like every other write ([[0044-django-is-the-engine]]), and an aspect the engine has not
routed yet - ledger, pantry, fleet as of today - is simply not available to it.

**What is NOT decided here:** which aspects the head unit surfaces, what its UI is, whether it keeps
its own Room replica, and whether it ever writes rather than only reads. Those are build tickets,
not standing rules.
