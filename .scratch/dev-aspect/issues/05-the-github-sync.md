# The LEGION board feed

## What changed from charting

Charted as "the GitHub sync": an Edge Function on a cron pulling issues and PRs across every repo
Kevin owns, into Supabase. Kevin narrowed the scope on 2026-09-01 - *"honestly github stuff i only
care about legion for now"* - and at that scope the whole design collapses into something far
smaller and strictly better.

**LEGION has no GitHub issues. Its pending work is ticket frontmatter in `.scratch/*/issues/`.**
That frontmatter is already parsed by `tools/pending_wiki.py`, already regenerated by the commit
hook in `.claude/settings.json`, and already published to GitHub Pages as `docs/index.html`.

So: **emit a machine-readable `docs/board.json` beside it, and have the phone fetch that.**

- No Supabase table, no Edge Function, no cron, no GitHub API, no PAT, no rate limits.
- No delete discipline problem - the file is regenerated whole from the tickets every time, so a
  resolved ticket cannot linger. The failure mode ticket 05 was originally written to guard against
  does not exist in this shape.
- It cannot drift from the board or the wiki, because all three read `collect()` in the same script.
- It fits "no Kevin-hosted anything" (CLAUDE.md section 7) exactly: GitHub Pages already serves
  `docs/`, publicly, from `dev`.

## Build

1. In `tools/pending_wiki.py`, reuse `collect()` and write `docs/board.json`:
   `generated_at` (UTC ISO 8601), `totals` (open / ready / built / blocked / decisions / kiv), and
   per map: slug, title, open, ready, built, kiv, and its open tickets (num, title, type, status,
   detail, ready, blocked_by).
2. `generated_at` is load-bearing, not decoration - ticket 07 depends on it.
3. Keep it small. It is fetched over mobile data.

## The noise problem, which is the real design work

Grill question 3, unanswered and still live. LEGION has ~106 open tickets across ~31 maps. A
faithful answer to "what is pending on LEGION" is 106 items, which is useless spoken aloud.

The feed carries everything; **ticket 08 decides what is said.** The rollup belongs at the speaking
end, not in the file - putting it in the file would bake one summarisation choice into the data and
lose the detail the hands path needs.

## Verification

- `python tools/pending_wiki.py` writes both `docs/index.html` and `docs/board.json`, and the totals
  in the JSON equal the totals rendered in the HTML. Asserted by comparing them, not by eye.
- The four buckets (ready / built / blocked / kiv) sum to the live open count, as CLAUDE.md section
  12 requires. They did not, once, and three tickets were double-counted.
- Resolving a ticket and re-running removes it from the JSON.
- The commit hook regenerates it. Verified by planting a change and watching a real commit stage it.
- `docs/board.json` is reachable at the Pages URL after a push. **A correct file in an unpushed
  commit is a stale public feed** - CLAUDE.md section 13 learned this the hard way.

### What the sentinel test found

The hook re-ran `pending_wiki.py` but **its `git add` list never named `docs/board.json`.** A commit
that edited a ticket would have published a regenerated `index.html` beside a stale feed - the wiki
and the phone disagreeing, which is precisely what generating both from one `collect()` exists to
make impossible. Fixed in `.claude/settings.json`, then re-verified: sentinel planted, bare
`git commit`, sentinel present in the regenerated and staged `board.json`.

**A second finding, recorded because it weakens the backstop generally.** The hook matches
`Bash(git commit*)` as a prefix, so a commit written as `git add X && git commit ...` never trips
it. Not a bug in the hook, but the backstop is absent whenever a commit is chained behind anything,
which is the common shape. Worth a follow-up if the wiki ever looks stale again.
