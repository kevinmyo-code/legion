# The engine as an MCP server

**Kevin, 2026-10-02:** *"yes to django as an mcp server. we could let the voice model or any other
model query it directly in the app. in the dev side also you could query it while were building
together."*

## Destination

**Decisions, plus a working read-only slice.** Every question below answered, so the engine's MCP
surface can be built without a taste call left in it, and one read-only path proven end to end from
Claude Code against the real engine. Shipping the whole surface to every client is past the
destination; the build tickets here are the route to it, not the destination itself.

## The three callers, and why they are not the same problem

| Caller | Transport it can use | Auth it can carry | What is different about it |
|---|---|---|---|
| The phone's Gemini Live session | None natively: the phone speaks a raw WebSocket to Gemini, so something on the phone has to bridge | The device token it already has | Must still work, for reads, when the engine is down (ADR 0044 rule 4). Live re-bills every declaration every turn |
| Claude Code, while building | stdio, or Streamable HTTP with a custom header | A device token in an env var | Already has the `pg` MCP: raw SQL, restricted mode, no household scope. This one would go through the same choke point the phone does |
| Any other client (claude.ai, ChatGPT, the Gemini app) | Streamable HTTP over public HTTPS only | OAuth 2.1, which the engine does not do today | Not bound by LEGION's prompt layer. `CANNOT_CLAUSE` does not reach it, so honesty has to live in the tool RESULT |

## What exists, so nothing here is invented (traced 2026-10-02)

- **Auth:** `household/authentication.py` `DeviceTokenAuthentication`, header `Authorization: Token
  <key>`, one token per device, revocable alone (ADR 0044 rule 3). Then `SessionAuthentication` for
  the browser. Permission `IsHouseholdMember`.
- **Tenancy choke point:** `household/tenancy.py` `household_of(request)` and `scoped(model,
  request)`; `TENANT_TABLES` (43 names) is checked from both directions by `tests/test_tenancy.py`.
  Postgres RLS (`web-and-households` 02b) is still not built, so the choke point is Python only.
- **API:** `api/urls.py` generates the synced routes from `api/registry.py`; the gate is
  `api/ingest/statement` and `api/ingest/receipt` (`ingest/`). Five gated tables are GET-only and a
  write to them answers 405 naming the gate. `server/openapi.yaml` is regenerated by `manage.py
  spectacular` from drf-spectacular. `feat/openapi-clients` (unmerged) generates the phone's DTOs
  from it.
- **Runtime:** gunicorn, WSGI, 2 workers, `--timeout 60` (`server/entrypoint.sh`). Deployed to Cloud
  Run, public HTTPS, min-instances 0, measured 5.4 s cold start. The Oracle VM was dropped 2026-09-10.
  Postgres is still Supabase's.
- **The phone's tools:** `LiveToolbox.kt` (7,856 lines) runs every tool ON THE PHONE, against Room,
  controllers, OBD, Spotify, Gmail. `EngineToolbox.kt`'s nine aspect-engine meta-tools write Room's
  `EngineRecord` and **have no server counterpart at all**: no `engine_records` table in `server/`.
  ADR 0044's own context names the problem this map addresses: *"the assistant's 112 tools welded to
  Kotlin"*.
- **Mail never reaches the server.** Gmail is read on the phone and excluded at the write sites
  (`LiveToolbox.EPISODIC_EXCLUDED_TOOLS`). That is what keeps it out of an engine MCP surface, and the
  phone bridge must not create a path around it.
- **Repo MCP servers already exist** under `tools/mcp/` (board, gradle), pinned `mcp>=1.2,<2`.

## Web facts this map leans on (web-sourced 2026-10-02, verify before building on them)

- MCP spec **2026-07-28** is current: no `initialize` handshake, no `Mcp-Session-Id`, every request
  self-describing, `server/discover` required, Tasks moved to an extension, Dynamic Client
  Registration **deprecated in favour of Client ID Metadata Documents**. Stateless plain
  request/response is a good fit for WSGI on Cloud Run at min-instances 0.
- The official `mcp` Python SDK **2.2.0 (2026-09-07)** claims 2026-07-28 support, Streamable HTTP,
  and a `TokenVerifier` for resource-server auth.
- `django-mcp-server` (gts360) runs on WSGI and accepts DRF authentication classes, but its docs cite
  spec 2025-03-26. Unverified for 2026-07-28.
- The Gemini API's MCP support is in Google's SDKs (Python/JS), client side. Nothing found says the
  Live WebSocket protocol speaks MCP. Unverified.

## Decisions so far

- **02 (research, 2026-10-02):** SDK 2.2.0 can be driven from WSGI per request. `django-mcp-server`
  breaks on SDK 2.x. DCR is the only OAuth registration every target client shares. Gemini Live has
  no MCP, so 04's bridge is the only path.
  [research](research/02-sdk-django-and-client-support.md)
- **01, 03, 05, 06 (Kevin, 2026-10-02):** inside Django at `/mcp`; a curated Python registry; device
  tokens with a read/write scope now, OAuth later; read AND write in v1.
- **04, 07, 08, 06.2 (Kevin, 2026-10-02, "go with your recs"):** one `ask_engine` bridge tool on the
  phone (11 builds it); no ingestion over MCP until the statement CSV format exists; Cloud Run, off by
  default behind `LEGION_MCP`, throttled per token, every call audited; memory tables excluded.
- **10 built (2026-10-02):** `server/engine_mcp/`, 11 tools, owes a live run.

## Not yet specified

- **The aspect engine has no server half.** `list_aspects`/`describe_aspect`/`query_records` are the
  most MCP-shaped tools LEGION has, and they read Room only. Whether `EngineRecord` moves to Django is
  a prerequisite for exposing them, and probably its own map.
- **MCP Apps as the reporting layer.** §1 calls widgets the reporting layer; an MCP App could render
  a ledger month inside claude.ai. Unclear whether that is a want.
- **Tasks extension** for long-running work (analysis, Canvas sync) once anything long runs on demand.
- **`subscriptions/listen` vs the phone's 60 s poll.** Probably irrelevant to the phone (it is not an
  MCP client for sync), but relevant if a third-party client wants change notifications.
- **The head unit** (ADR 0048, unmerged) as a fourth caller.
- **Resources and prompts.** Tools only for now; whether the docs or a household summary should be
  MCP resources is fog.

## Out of scope

- **Mail, or any third-party content, through the engine.** It never reaches the server (§7), so it
  cannot be an engine tool. Ruled at charting, not a ticket.
- **An MCP surface Kevin hosts for other households.** The household hosts its own (§7, ADR 0045).
- **Replacing the REST sync contract with MCP.** The limbs keep syncing over REST.
- **Exposing the `pg` MCP beyond development.** It is raw SQL with no household scope.
